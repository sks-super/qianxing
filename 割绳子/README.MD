用于由 Lua 驱动千星奇域客户端 UI 开发、诊断和维护。本文只规定创作者前置操作、实现原则、调试方式和查阅 API 文档的方法，不承担 API 参考手册的职责。任何具体类型、函数、字段、枚举、参数、返回值和数值范围，都必须以任务执行时找到的当前 API 文档为准；不要用本文、普通 Lua、Unity、其他 UI 框架或模型记忆补全未知能力。

## 开始工作前必须遵守的约束
0. 每次开始工作前，都必须阅读一遍本文档。可以拷贝一份作为AGENTS.MD文件
1. 每次收到新需求或需求发生变化时，先按第三节找到并确认当前使用的 API 文档。确认之前，不要编写依赖编辑器 API 的代码。
2. README、旧脚本、示例代码、测试代码和模型记忆都只能作为检索线索，不能作为 API 依据。具体写法只能来自当前 API 文档。
3. 实现每项功能前，先在当前 API 文档中定向核对所需类型、创建入口、调用形式、参数、返回值、字段读写性、枚举、数值范围、回调约定、生命周期和对应的清理方式。颜色、图片、输入、布局、脚本挂载和日志属于高风险项，每次使用都要重新核对。
4. 写完代码后，提取代码中所有编辑器 API 标识并逐项回查当前 API 文档。任何一个具体标识、调用形式或参数都找不到依据时，不得交付。
5. 遇到 API 文档缺失、版本冲突或行为说明不清楚时，把受影响能力标记为 `unknown` 并停止依赖它的实现。先重新检索文档；仍无答案时再向创作者索要当前文档或必要事实。最小探针不能代替缺失的文档。
6. API 文档发生变化、被替换或版本重新确认后，立即废弃此前缓存的 API 结论，并按新文档重新检索和审查代码。
7. 修改正式小游戏脚本前，先按第二节完成两轮信息交接。没有取得客户端控件容器、实际挂载脚本和本次所需控件的真实信息时，不要继续；不要猜值、填写临时 ID，也不要要求创作者换一种格式重发。
8. 所有由 Lua 创建或注册的原生控件、监听、动画任务和加载任务，都必须交给同一个 Runtime 管理。创建成功后立即记录；启动失败或脚本销毁时，按创建顺序的相反方向释放。
9. 先完成 Runtime 初始化、客户端控件容器与脚本挂载检查，以及错误日志处理，再创建页面和玩法。发生致命错误时，立即进入 `FAILED`，并停止接收输入、加载内容和执行逐帧逻辑。
10. 只修改创作者指定的内容，保留其他已有改动。新生成的候选文件没有验证通过前，不要覆盖正式文件。
11. 每个重要结论都要按 6.1 分别写清证据来自哪里，以及是否经过真实运行验证。没有在真实编辑器或游戏运行环境中验证过，就不要写成“真机通过”。
12. 读取大型文档或数据标注时，只搜索当前需求涉及的内容。不要一次读取整个文件。
13. 只有游戏确实需要某种图片资产时，才按 3.1 向创作者索取对应的图片资产 ID。图片来源类别和绑定方式由 AI 查询当前 API 文档与资源记录确定，不让创作者猜接口参数。
14. 图片控件第一次显示前，必须按 3.1 和 4.4 完成资源确认、图片绑定和结果核对。任何一步失败都不要继续使用这张图片；不要猜图片资产 ID，也不要把 UI 控件索引当成图片资产 ID。
15. 游戏尚未完成时，不要要求创作者点击、拖动、拖拽或校准。游戏可以正常游玩后，只有创作者主动要求测试或报告输入问题时，才使用游戏中已有的按钮和可拖动物体进行验证。
16. 编写依赖鼠标或触摸位置的逻辑前，先按 4.5 从当前 API 文档确认事件处理方式和坐标规则。坐标含义没有确认时，不要自行猜测。

## 一、采用以下编辑器约束

### 1.1 这是受编辑器约束的 Lua 运行环境

编辑器中的 Lua 版本、标准库裁剪范围和额外扩展都可能与通用 Lua 环境不同。开始实现前，从当前 API 文档核对：

- Lua 语言版本和语法边界；
- 可用、被裁剪或被替换的标准库；
- traceback、时间、数学等扩展能力；
- 文件系统、网络、动态模块和原生对象构造是否开放；
- 是否提供计时器，以及计时器属于哪个时间域、如何取消。

文档没有声明的能力一律视为不可用。若没有文档化计时器，需要计时功能时由 Runtime 使用已确认的逐帧时间源和队列实现，不得凭空调用常见框架中的计时器。

### 1.2 将 Lua 状态映射到编辑器原生 UI 控件

画面由 Lua 状态驱动编辑器提供的原生 UI 控件。图片、文字、滚动文字、输入区域、按钮和运行时父组分别需要哪种控件，必须根据本次需求在当前 API 文档中查询，README 不保存 subtype 名称。

控件通常来自创作者预先建立的客户端控件模板。创作者提供的是模板“索引”；Lua 如何实例化、父级参数接受对象还是标识、返回什么基类或具体类型，都必须在当前 API 文档中确认。模板索引、运行时实例 ID、父控件和图片资产 ID 是不同概念，不得互换。

### 1.3 按编辑器生命周期组织代码

脚本由编辑器生命周期驱动，不要从文件顶部启动永久循环。实现前必须查询当前 API 文档列出的初始化、启动、启用、禁用、逐帧更新、关卡时间更新和销毁入口，并核对每个入口的参数、调用条件和时钟语义；README 不保存这些回调的具体名称。

创建控件、注册监听或启用逐帧更新时是否会同步重入，也必须以当前 API 文档和真实运行证据为准。文档未说明时标记为 `unknown`，用状态 guard 防止重复进入；只有在真实编辑器中直接观察到，才能标记为 `observed`。

生命周期回调已经发生，只能证明脚本进入了该回调，不能证明编辑器提供的所有外部对象和运行时数据已经同时就绪。挂载容器、脚本查询结果、画布信息和其他启动依赖必须分别判断；某一项此刻取不到，不等于配置错误，也不等于其他依赖同样未就绪。

启动检查必须区分三种结果：创作者提供的配置缺失或格式错误属于确定的配置错误；运行时对象尚未出现或尚未存活属于 `not_ready`；对象已经就绪但身份明确不符属于确定的不匹配。只有第一种和第三种可以立即失败，`not_ready` 必须留在启动状态并经过有界重试，不能被写成“不匹配”。

### 1.4 明确编辑器日志行为

当前版本有哪些普通、警告和错误日志入口，以及它们是否会抛错、停止脚本或只写日志，必须从当前 API 文档确认。README 只规定第五节的聚合策略，不声明具体日志函数及其行为。

## 使用 API 前必须掌握的知识

### 颜色格式不能套用常见框架经验

本引擎的颜色构造方式、点号或冒号调用形式、通道顺序、通道数值范围、整数要求、alpha 含义、省略 alpha 的行为和颜色读回方式，都必须从当前 API 文档核对。默认使用 `0–255` 整数，无浮点；先确认文档，再把外部设计值显式换算到文档要求的格式。

### 点号、冒号和字段赋值

编辑器 API 可能同时包含全局函数、实例方法和直接字段。每使用一个标识，都要从当前 API 文档确认：

- 是点号调用、冒号调用还是字段读写；
- 字段是只读还是读写；
- 参数的顺序、可选性和实际类型；
- 返回零个、一个还是多个值；
- 返回值是否允许链式调用；
- 是否存在配对的注销、停止或销毁入口。

不要仅凭名称、旧代码或其他 Lua 框架的习惯选择调用形式。方法只有在当前文档明确返回可继续调用的对象时才能链式调用。

### 多返回值和编辑器对象

编辑器对象不一定能用普通 Lua 类型判断区分 subtype。使用专用字段前，先从当前 API 文档确认返回对象的声明类型、存活检查方式、运行时类型检查方式以及安全转换方式。

API 也可能返回多个独立 Lua 值，而不是向量、颜色或结构体对象。调用前必须按当前签名确认返回值数量、顺序和含义；禁止凭字段名习惯假设返回对象带有 `x/y` 等成员。

根控件、父控件、模板索引、运行时控件 ID、脚本实例和挂载容器是不同对象。查询与创建各自接受哪种标识、父级参数是什么类型、当前脚本如何取得挂载对象，都由当前 API 文档决定。

### 脚本时钟、脚本开关和控件状态

编辑器可能同时存在脚本时间、关卡时间、脚本启用状态和逐帧更新开关；这些概念不能自动视为同一个时钟或开关。根据玩法需要，从当前 API 文档确认暂停行为、回调时间域、启停方式和恢复语义。

控件的“启用”“在层级中生效”“可见”“可命中”和“父级关系”也属于不同概念。先查询当前 subtype 公开哪些状态、哪些只读、哪些可写，以及每种状态对脚本和输入的影响，再决定设置顺序。

同级顺序、子级查询、路径查询及其索引基准必须从当前 API 文档确认。不要假定索引从 0 或 1 开始，也不要假定直接子级查询支持层级路径。

### 枚举、按键和文本字段

枚举参数必须使用当前 API 文档声明的枚举类型和值，不能用字符串、猜测的整数或其他框架中的同名枚举替代。枚举对象本身公开哪些说明字段，也要现查文档。

按键提示、按键监听、设备类型、按下/抬起阶段、回调返回值和事件消费语义都可能不同于常见 UI 框架。使用前逐项查文档；如果文档没有解释回调返回值含义，就保持 `unknown`，不要猜。若注销监听要求原回调引用，Runtime 必须保存注册时的同一引用；具体要求仍以当前文档为准。

文本内容、字体、颜色、背景和对齐可能通过字段或方法设置。不要假设存在常见的文本 setter、第三方文本组件或惯用的对齐枚举名称；按当前文档实际声明实现。

### 当前 API 的数值与布局语义

布局可能使用独立数值、多参数方法或编辑器对象。实现前查询当前 API 文档是否存在向量、矩形、锚点、轴心、缩放和位置对象，禁止自行引入常见框架的构造类型。

锚点、轴心、旋转、填充、滚动、羽化、尺寸和坐标的单位、范围、原点、轴方向与作用域都必须由当前 API 文档说明。名称相似不构成数值契约；文档没有给出的部分仍是 `unknown`。

数学辅助函数同样属于运行环境能力。有限数检查、钳制或其他扩展只有在当前 API 文档明确存在时才能调用；否则使用纯 Lua 且与当前语言版本兼容的实现。

## 二、实施前要求创作者完成以下内容

要求创作者在编辑器中完成这些步骤。不要尝试用 Lua 代码代替编辑器配置。

### 2.1 先建立客户端脚本入口

第一阶段必须把“创作者要做什么”和“创作者需要提供什么”分成下面两个独立段落。不要编号，不要拆成微操作，不要在这两个段落之间插入解释：

> 请前往【界面控件组管理】，在对应的【界面布局】中，点击【添加界面控件】，然后在【预制模板】中创建【客户端控件容器】，而后在右边的【画布设置】中，点击【前往编辑】，在【脚本】页签中点击【添加脚本】，并选择一个 Lua 脚本，例如 `levelScript`。（相关详细流程可以查阅千星奇域说明书）。

> 完成后，请在【客户端控件容器】-【画布设置】-【前往编辑】中，请把【容器节点】的索引，以及实际挂载的 Lua 脚本名称或地址发给我，例如 `levelScript`。这样我们可以开始下一步。（注意，一定要在【客户端控件容器】的【容器节点】上挂载好这个脚本哦~）

第一段只负责说明操作，第二段只负责索取两个值。第一阶段不得索取普通控件模板索引，不得要求创作者另行回复“客户端脚本已挂载：是”，不得推荐创建 `angry_birds` 等新脚本名；`levelScript` 只作为已有或可选 Lua 脚本的示例。

收到容器索引和脚本信息后，不限制创作者发来的是名称、相对路径还是绝对路径。AI 必须先去掉首尾空白和包裹引号，把反斜杠视为路径分隔符，取最后一个非空路径片段；若该片段以 `.lua` 结尾，则去掉该后缀，并保留其余字符的原始大小写。例如 `levelScript`、`Scripts/levelScript.lua` 和 `E:\Project\Scripts\levelScript.lua` 都归一化为 `levelScript`。只把归一化结果写入 `EXPECTED_CLIENT_SCRIPT_PATH`，不得把创作者发来的原始完整路径直接写入该字段，也不得要求创作者按另一种格式重发。AI 不得修改一个脚本，却让容器挂载另一个脚本。

创作者提供这两个值不能代替运行时验证。开始正式玩法逻辑前，先在当前 API 文档中查明如何取得当前脚本实例、挂载容器、脚本运行时名称，以及如何从容器查询已挂载脚本。然后确认这些对象均有效、运行时脚本名称与 AI 归一化后的短名称逐字相同、容器查询到的脚本实例就是当前实例。具体字段和方法名只从当前 API 文档取得，不从 README 复制。配置值本身缺失或格式错误时立即停止；运行时对象暂未取得时记录为 `not_ready` 并进入启动就绪重试；只有对象已经就绪且核对结果明确不一致时才判定挂载失败。未通过最终核对前不得声称脚本已经正确挂载，也不得创建玩法资源。

注意不要卡思考，需要用户提供内容时必须输出内容！告诉用户要什么！
工程已有合适的客户端控件容器和已挂载脚本时允许复用，但仍要取得容器索引和实际挂载脚本名称；创作者若发来路径，由 AI 自行归一化。

编辑器中的“客户端控件容器”的“容器节点”是脚本挂载入口，“容器节点”是客户端控件容器下的根节点，其索引必须由创作者提供；脚本中使用的动态创建的实例都基于容器节点并以其为父节点。客户端控件容器索引（服务器索引）、容器节点索引（客户端索引）和动态实例的运行时 ID 是三种不同标识，禁止混用。

### 2.3 创建 Lua 可以实例化的 UI 元件

只有第一阶段的客户端控件容器索引和实际挂载脚本信息都已收到，才发送第二阶段。中文创作者必须收到以下格式：

## 四、按以下规则构建 Lua 小游戏引擎

### 4.1 分开 Runtime 与游戏逻辑

即使全部代码放在一个 Lua 文件中，也只需区分两类职责：

- `Runtime`：核对脚本挂载，记录当前状态，登记并清理资源，聚合错误日志。
- 游戏逻辑：在 `BuildGameResources` 中创建本次需要的内容，在 `UpdateGame` 中推进玩法和 UI。

每个需要释放的控件、监听、动画任务或加载任务创建成功后，立即在 Runtime 中登记释放动作。具体注销、停止和销毁入口必须从当前 API 文档查询；游戏逻辑不自行维护另一套生命周期或错误状态。

### 4.2 使用明确状态机

```text
NEW → STARTING ↺ → RUNNING
STARTING 或 RUNNING → FAILED
任意状态 → DESTROYED
```

- `NEW`：尚未启动。
- `STARTING`：先验证静态配置，再分别等待启动依赖就绪；全部就绪并完成身份核对后才创建本次需要的资源。
- `RUNNING`：推进玩法。
- `FAILED`：停止逐帧逻辑，执行清理，并只输出一个聚合故障块。
- `DESTROYED`：执行最终清理；重复调用不产生额外效果。

`Runtime.failed` 用于阻止同一主故障重复输出。状态名称和转换必须与第五节骨架保持一致。

每项启动依赖都必须有独立的就绪结果和统一的有界重试记录，包括最后一次未就绪原因、已尝试次数与重试预算。一次回调中未就绪只结束本次尝试，不进入 `FAILED`，不创建玩法资源，也不开放输入。预算耗尽才输出一次聚合故障；依赖在预算内就绪后只允许完成一次初始化。配置错误和已经取得对象后的确定不匹配不参与重试。

### 4.3 按安全顺序启动

```text
Runtime.state = STARTING
→ 验证创作者提供的配置是否完整且格式有效
→ 按当前 API 文档分别探测脚本上下文、挂载容器及其他启动依赖
→ 任一依赖尚未就绪：记录原因并在后续已文档化回调中有限重试
→ 全部依赖就绪：核对挂载关系；确定不匹配才进入 FAILED
→ 创建本次玩法资源
→ 每个资源创建成功后立即登记清理动作
→ Runtime.state = RUNNING
→ 让已启用的启动就绪回调开始进入玩法分支；若玩法另有回调，先发布 RUNNING 再启用
→ 通过当前文档声明的普通日志入口输出一次启动汇总
```

调用创建控件、注册监听或启用逐帧回调前，必须先准备好这些调用可能读取的状态并设置防重复 guard。为推进启动就绪重试，可以在完整发布 `STARTING`、重试计数和重入 guard 后启用逐帧入口，但该状态下只能执行一次就绪尝试，禁止推进玩法。玩法专用回调仍须先进入 `RUNNING` 再启用；若启动与玩法共用同一逐帧入口，切换状态即可，不得重复注册或重复启用。任一步失败时只进入一次统一失败处理，由它停止逐帧逻辑、执行清理并输出错误块。

### 4.4 控件创建与图片绑定

#### 4.4.1 控件创建约束

创建任何控件前，先在当前 API 文档中查明准确 subtype、创建入口、模板索引参数、父级参数、返回类型、存活与类型检查方式、显示状态、输入命中状态以及销毁入口。没有查到的字段或方法不得写入代码。

```text
按当前文档创建
→ 立即登记所有权
→ 使用文档声明的方式关闭输入命中并保持不可见
→ 只写入真实 subtype 已文档化的属性
→ 按当前颜色契约构造并核对颜色
→ 使用文档声明的方式启用控件
→ 仅在文档或真实证据表明启用会重置属性时重提关键属性
→ 核对当前文档允许读回的关键状态
→ 最后显示
→ 最后开放输入命中
```

创建后、登记前报错会泄漏孤儿控件；过早显示会露出半配置画面；过早开放输入命中会让隐藏页面抢输入。

每个实例至少核对以下语义；具体字段和检查函数由当前 API 文档决定：

```text
创建结果存在
若文档公开存活状态，则实例仍然存活
运行时实际类型与本次预期 subtype 一致
```

#### 4.4.2 图片控件知识

实例化图片控件只表示获得了控件对象，不等于图片资源已经绑定。控件模板索引、图片资产 ID 和运行时控件 ID 是三种不同标识。图片资源绑定、图片显示模式、颜色着色、控件启用和控件显示也是不同操作；给图片着色不能代替选择并绑定图片资源。

准确的图片 subtype、资源来源参数、绑定入口、图片模式、颜色字段、状态读回方式和调用顺序必须从当前 API 文档查询。README 不保存这些标识或枚举值。

#### 4.4.3 图片绑定约束

不得依赖图片控件模板中的默认图片，也不得把问号或其他占位图当成成功结果。每个新建或重新启用的图片实例在首次显示前按以下语义执行：

```text
确认图片资产 ID 与资源记录
→ 从当前 API 文档确认资源来源参数、绑定入口、图片模式和颜色格式
→ 保持控件不可见且不可命中
→ 按文档绑定图片资源
→ 按文档设置本次实际需要的图片模式与颜色
→ 按文档启用控件
→ 若文档或真实证据表明启用会重置图片属性，则重新提交受影响的属性
→ 读取文档明确公开的状态并核对；文档没有读回能力时不要虚构字段
→ 设置位置和尺寸
→ 最后显示，需要交互时再最后开放输入命中
```

如果绑定调用报错、文档支持的读回结果不一致、画面仍是问号或缺图占位符，或状态切换后恢复成模板默认资源，立即进入 `FAILED`；在解决前不得继续使用该图片资源。图片模式和资源来源只接受当前 API 文档、创作者提供的资源记录，或创作者明确委托 AI 选图时提供的数据标注作为证据，不得猜测。

### 4.5 输入知识与实现约束

#### 4.5.1 先查清输入 API 契约

##### 前置知识

###### 手柄导航的默认行为

当控件开启“可被手柄摇杆导航选中”时，编辑器会默认启用内置的方向导航。手柄摇杆向左、右、上或下输入时，编辑器会自动选择对应方向上距离当前控件最近的控件。方向判断和目标控件选择由编辑器完成。使用相关手柄导航配置方法后可以改变跳转，但除非需求明确要求，否则一般按照默认逻辑即可。

###### 当前聚焦控件

同一时刻全局只有一个当前聚焦控件。方向导航以当前聚焦控件为起点；没有当前聚焦控件时，手柄导航输入通常不会被界面消费。

###### 导航隔离区域

开启“隔离手柄导航”的容器会形成独立的导航区域。“距离最近”只在当前导航隔离区域内搜索；当前控件不属于任何导航隔离区域时，整棵控件树共同参与搜索。

###### 手柄导航事件

一次左摇杆离散方向输入既会参与默认的聚焦移动，也可能产生对应方向的手柄导航事件，两者来自同一次输入。确认和取消事件只会发送给当前聚焦控件，并且不会自动执行具体业务。当前聚焦控件发生变化时，相关控件会分别进入聚焦或退出聚焦。

###### 聚焦控件销毁

当前聚焦控件被销毁时，运行时会清空当前聚焦并使该控件退出聚焦，不会自动选择下层界面的其他控件。

输入事件位置、无事件时取得的位置、控件布局位置、画布尺寸和玩法逻辑位置可能来自不同坐标域。名称相似、数值范围接近或都带有“UI”“位置”等字样，均不能证明它们具有相同原点、方向、单位、缩放或作用范围，也不能证明它们可以直接比较或换算。

布局位置和布局尺寸描述的是布局请求或布局状态，不自动等于控件最终显示范围或实际命中范围。父级、锚点、轴心、缩放、裁剪、层级和运行时布局都可能参与最终结果；仅取得画布宽高也不能反推出输入位置的原点和坐标域。

由编辑器判断某个控件是否被命中，与脚本读取位置后自行计算命中，是两种不同的输入架构。前者可以不依赖坐标换算；后者只有在输入、布局、画布和玩法坐标之间的关系已经由当前 含有API信息的相关文档 明确，或经允许的专项探针取得真实证据后才成立。

`unknown` 是有效且必须保留的知识状态，不是允许根据经验补全的空白。当前 含有API信息的相关文档 没有公开坐标转换或最终命中范围能力时，README、旧脚本和试出来的数值都不能替它创造这种能力。

##### 实施约束

输入最容易因套用常见框架经验而写错。实现点击、悬停、拖拽、命中判断或位置换算前，必须重新在当前 含有API信息的相关文档 中定向查清：

- 哪种控件能够接收输入，以及如何注册和移除监听；
- 当前版本实际存在的事件类型，禁止凭空补出“移动”“鼠标移动”等事件；
- 回调接收几个参数、参数顺序和类型，禁止默认写成 `(x, y)`；
- 如何读取当前位置、按下位置、位移、触点身份和拖拽状态，以及每项返回几个值；
- 是否允许在没有事件时轮询指针位置；
- 如何取得 Canvas 尺寸，以及返回值的数量、单位和有效范围；
- 位置与位移的原点、Y 轴方向、单位、作用域和坐标域；
- 控件尺寸读回代表布局增量、局部尺寸还是最终命中矩形；
- 注册监听是否可能同步触发回调；
- 测试或模拟输入会产生哪些事件及其顺序。

当前文档没有明确的项目保持 `unknown`。尤其不能从方法名推断事件位置是屏幕像素、Canvas 左上坐标、控件局部坐标或游戏逻辑坐标，也不能默认事件位置与轮询位置同域。

只要实现准备把事件、轮询、布局、画布或玩法中的两个数值放进同一个公式、范围判断或位置比较，就必须先从当前 含有API信息的相关文档 找到两者关系的明确依据。查不到时不得编写该计算；不得通过尝试多种原点、轴向、缩放或偏移，再选择一个“看起来能命中”的结果。

#### 4.5.2 输入监听与状态约束

输入状态分为三层：

```text
原始事件队列：只收集当前 API 文档存在的事件，保留原始顺序、时间和参数
编辑器帧快照：归一化位置、是否按住、活动触点、捕获目标、是否拖拽
玩法输入状态：按下、释放、单击、拖拽开始、拖拽移动、拖拽结束
```

不得虚构 API 文档未列出的输入事件。需要轮询指针位置时，轮询结果必须单独确认坐标转换，不能直接送入 HitTest。回调只负责按当前签名采样原始数据，再由统一输入适配器归一化；不要在不同回调中各写一套转换。

把每个回调引用保存在 Runtime 记录中。移除监听时按当前 API 文档要求使用正确的事件身份和回调引用；若要求同一函数引用，禁止用新建匿名函数移除。注册监听前准备好事件队列和防重复 guard，注册中途失败时只撤销已经登记的监听。不得把同步触发写成 `documented`，只有真实观察到后才能标记为 `observed`。

不得把位移当作当前位置，也不得把原始事件位置、Canvas 坐标和逻辑坐标混存在同一组字段中。

#### 4.5.3 坐标实现约束

如果本次玩法需要位置或自定义 HitTest，在启动和 Canvas 变化时使用当前 API 文档声明的 Canvas 尺寸查询能力。宽高只有同时满足文档数值契约并且是有限正数时才有效。初次查询无效不证明编辑器永久失败：记录“Canvas 尚未就绪”，关闭玩法输入并保持未进入 `RUNNING`，在后续已文档化回调中按源码明确配置的有限预算重试；不得阻塞循环，也不得每次各打一条日志。预算耗尽仍无效时才进入 `FAILED`，一次性报告尝试次数和最后结果。运行中尺寸暂时无效时同样暂停输入并有限重试，禁止继续拿旧尺寸处理新事件。画布不是唯一允许重试的启动依赖；挂载容器、脚本查询结果及其他由编辑器提供的启动对象都必须遵守 4.2 的同一套就绪分类和有界重试规则。

任何阶段都禁止把屏幕分辨率、经验尺寸或其他猜测值当作 Canvas 尺寸。Canvas 尺寸只服务于真正需要坐标的玩法输入、viewport、Renderer 和 HitTest。

只有玩法读取指针位置或采用自定义统一逻辑 HitTest 时，才为输入适配器保存以下坐标字段；原生命中且不读取位置时整体记录为 `not_required`：

```text
Canvas 宽高、就绪状态、重试次数和重试预算
逻辑画布宽高
缩放比例和 viewport 边界
事件位置契约
轮询位置契约（仅在当前 API 文档支持轮询且玩法需要时）
位移契约
契约证据和验证错误
```

当 4.5.1 所列坐标语义仍为 `unknown` 时，不得从名称推断，也不得因此自动要求创作者点击校准图形。按以下顺序处理：

未知关系不是先写坐标实现再等待验证的理由。任何依赖该关系的自定义命中、绝对位置比较或布局移动都不得进入正式实现；此时只有两条合法路径：改用不读取该坐标关系的编辑器原生命中，或者停止对应功能并明确指出 含有API信息的相关文档 缺少什么。

1. 原生按钮或局部输入区域只依赖编辑器命中结果、玩法不读取位置时，不建立坐标转换，不显示校准点；在内部事务层保证一次物理操作最终只生成一次动作。
2. 拖拽实际玩法对象时，代码必须按当前 API 文档提供的触点身份维护按下、移动和释放事务，并能在诊断开关开启时聚合记录起点、终点、累计位移、事件顺序和对象最终位置。这是实现知识，不是创作者的前置拖拽任务。
3. 只有自定义统一逻辑 HitTest 已经出现实际坐标错乱、文档仍无法确定转换，且创作者明确同意专项调试时，才允许提出多点校准。它是异常升级路径，不是初始化模板；禁止默认生成“五个菱形”“中心加四角”或其他固定五点流程。
4. 确需仿射求解时，使用三个互不共线的求解样本和至少一个独立验证样本；目标坐标必须来自已经验证的 Renderer/布局契约。仿射变换只能标记为项目侧 `inferred` 策略，验证误差通过后才标记为 `observed`，不得描述成 API 事实。
5. 若使用轮询位置，必须为当前文档声明的轮询结果单独验证变换。只有证据证明它与事件位置同域时才允许共用转换；否则保留两个转换函数。

禁止把输入位置直接与布局位置、布局尺寸、画布边界或玩法边界比较；禁止把输入位移直接加到布局位置；禁止把画布宽高当作输入坐标原点或范围的证明。只有当前 含有API信息的相关文档 明确说明了所需关系，或专项探针已经把完整转换链标记为 `observed`，这些运算才允许存在。

确实需要坐标转换时，只允许集中在 Input Adapter 中，至少提供：

```text
事件位置归一化：原始位置 → 逻辑位置与是否位于 viewport 内
轮询位置归一化：原始位置 → 逻辑位置与是否位于 viewport 内
事件位移归一化：原始位移 → 逻辑位移
```

采用统一逻辑坐标时，先根据已经确认的编辑器坐标契约转换到 Canvas，再转换到项目选择的统一逻辑坐标。Renderer、HitTest、拖拽和 HUD 必须共享同一个逻辑坐标定义。原始坐标只能存在于编辑器适配器；World/Game 禁止读取原始 UI 坐标。原生命中且不读取位置时不要为了满足模板创建这些转换函数。

使用上述坐标转换时，Canvas 尺寸变化必须在提交新布局的同一个安全边界更新 viewport 和三个转换函数，并取消当前指针捕获，避免旧比例下的拖拽瞬移。禁止渲染已经使用新尺寸而输入仍使用旧尺寸。

#### 4.5.4 输入区域实现约束

实现前按以下优先级选择输入架构：

1. **原生控件命中（默认）**：由编辑器判断哪个按钮或局部输入区域被命中。只需要知道点击、进入、离开或拖拽发生在哪个区域时，每个区域分别保存自己的回调和区域身份，不读取位置反推命中目标；不得再在它们上方无条件放置一个开启命中的全屏输入区域。需要背景输入时，应使用不重叠区域，或先用同一次真机探针证明穿透与同级顺序仲裁符合预期。
2. **统一逻辑 HitTest（有条件）**：只有玩法确实需要脚本自行判断位置，并且当前 含有API信息的相关文档 或专项真机证据已经明确输入、布局、画布和玩法坐标之间的完整关系时，才允许使用一个覆盖目标交互区域的输入控件，在统一逻辑坐标中自行 HitTest。任一必需关系仍为 `unknown` 时不得选择该架构。与它重叠的原生按钮不得同时保持可命中，除非真机已经验证命中顺序、穿透和单次动作去重。

只有探针已经把混合架构的路由结果标记为 `observed` 时才允许混用，并且一次物理操作只能生成一次内部动作。输入区域由 AI 使用创作者提供的控件模板索引动态实例化，禁止要求创作者编辑其尺寸、位置、锚点或命中属性。

按以下事务顺序配置输入平面：

```text
实例化并立即登记所有权
→ 使用当前文档声明的方式关闭输入命中
→ 设置当前文档支持的锚点、轴心、尺寸和位置
→ 使用当前文档声明的方式启用控件
→ 在输入命中仍关闭时重提可能被重置的几何和输入字段
→ 注册并登记回调引用
→ 显示控件，并验证文档公开的生效状态、几何读回值和同级顺序
→ 最后开放输入命中
```

任何单一尺寸字段都不能在文档未说明时自动代表最终屏幕矩形或真实命中范围。必须记录当前 API 文档定义的锚点、轴心、位置、缩放、请求尺寸及可用读回值，并在玩法完成后的按需真机验证中，用实际交互区域确认覆盖。拉伸布局下尤其不能把尺寸增量直接称为最终宽高。

若还有其他可交互控件，必须按已选择的输入架构明确命中优先级。只能向真实 subtype 写入当前 API 文档明确公开的字段；事件穿透、光标显示等能力只有在文档和真实 subtype 都支持、且需求确实需要时才设置，不得凭名称猜测。

隐藏、脚本禁用、`FAILED` 和销毁时先关闭输入命中，再停止消费事件，并清除按住状态、活动触点、捕获目标、拖拽状态和未消费的玩法输入。脚本恢复时不得重复注册监听；恢复几何并验证后最后重新开放输入命中。

#### 4.5.5 点击与拖拽约束

如果当前 API 文档提供触点身份，每个活动触点按该身份维护一条事务；不支持多触点的玩法也必须忽略非当前活动触点的事件，不能让第二个触点覆盖第一个。若文档没有触点身份，不得虚构字段，应按文档实际能力设计单指输入。

下列位置处理只在所需坐标关系已经由当前 含有API信息的相关文档 明确或由允许的专项证据确认时执行；关系仍为 `unknown` 时只维护事件事务，不读取或换算位置。

```text
按下语义：归一化当前位置和按下位置；捕获活动触点与 HitTest 目标
拖拽开始语义：只有同一事务可以进入拖拽；只发送一次拖拽开始
拖拽移动语义：只有同一事务可以更新；坐标关系已确认时优先使用归一化绝对位置，位移只作单次增量
拖拽结束语义：只发送一次拖拽结束并释放捕获，不额外产生单击
释放语义：结束按住状态；仅在没有形成拖拽且释放规则满足时生成一次内部单击
完成/单击语义：若编辑器另有完成事件，用事务序号去重，不得重复执行玩法动作
进入/离开语义：只更新悬停；离开绝不自动产生单击，并按真实事件能力结束或保留捕获
```

实际事件名称和顺序只取自当前 API 文档；若使用模拟输入，还要单独查询其事件序列。内部事务必须把一次物理操作归一化为一次玩法动作，不能让释放事件和单击完成事件各执行一次。只有实际玩法出现重复点击、漏点或事件顺序问题时，才在对应玩法调试中聚合记录编辑器事件顺序。

只有当前绝对位置到玩法位置的关系已经由 含有API信息的相关文档 明确或被专项探针标记为 `observed` 时，拖拽才允许优先使用归一化后的绝对位置。只有输入位移到玩法位移的关系同样已经确认时，才允许累计位移或用它驱动布局对象。所需关系仍为 `unknown` 时，不得用绝对位置或位移猜测对象移动；能只依赖编辑器拖拽事件完成状态事务就不读取坐标，否则停止该拖拽实现并说明缺失事实。拖拽阈值使用已经确认的玩法坐标单位，并记录具体数值；低于阈值仍可视为点击，高于阈值后不得在释放时补发点击。

同一编辑器帧可能依次出现多个事件，必须保留完整顺序，并保证一次物理操作只产生一次玩法动作。脚本被禁用、进入 `FAILED` 或销毁时，显式丢弃未消费输入，防止恢复后补发旧操作。

### 4.6 分开管理运行、可见和输入命中状态

“对象参与运行”“画面可见”“接收输入命中”是三个不同概念。它们在当前 API 中分别对应哪些字段或方法、是否只读、状态切换有什么副作用，都必须现查文档。

| 逻辑状态 | 参与运行 | 画面可见 | 接收输入 |
| --- | --- | --- | --- |
| 正在显示的非交互图片 | 是 | 是 | 否 |
| 可交互按钮或命中区 | 是 | 按真实 subtype 决定 | 是 |
| 半初始化或失败对象 | 不应继续推进 | 否 | 否 |

隐藏顺序：先关闭输入命中，再隐藏，必要时停止对象运行。

显示顺序：先启用对象，按文档或真实证据重提会被重置的属性，再显示，最后开放输入命中。

## 五、在错误边界收口编辑器日志

### 5.1 聚合输出编辑器日志

先从当前 API 文档确认普通、警告和错误日志入口的准确名称、调用形式、参数和副作用。不得因为旧 README 或旧代码曾使用某个日志函数，就认为当前版本仍然存在或行为相同。无论错误日志入口是否会自动抛错，致命错误都由 Runtime 明确进入 `FAILED`、停止输入和加载、停止逐帧逻辑并回滚已登记资源。

日志先形成结构化记录，再一次性输出有界连续块：

- 正常启动或阶段完成只通过当前文档声明的普通日志入口输出一次汇总，禁止按字段分开打印。
- 可恢复异常按需要通过当前文档声明的警告入口输出一次；相同问题必须聚合计数，禁止逐帧重复。文档没有独立警告入口时，不得凭空调用常见名称。
- 每个主故障只通过当前文档声明的错误日志入口输出一次，并使用 `GAME FAULT BEGIN/END <错误码>` 包住完整连续块；第一个主错误决定错误码和 traceback，后续清理错误只能追加，不能覆盖首错。
- cleanup errors 先收集，最后追加到同一个故障块；禁止在清理循环中逐条打印。
- 没有新增高价值信息时，不得让同一故障在后续帧再次输出。

需要创作者提供诊断信息时，只请求对应错误码的完整 BEGIN/END 连续块，或直接请求一份编辑器日志文件；不得让创作者逐条复制十几行日志，也不得来回搜索多个关键词。

只在当前 API 文档声明的启动、逐帧更新和清理入口等完整事务边界建立错误边界；受保护调用和 traceback 能力也必须先确认运行环境支持。不要给每个 getter、setter 或纯 Lua 内部函数单独套保护调用。如果编辑器日志无法取得，一次性向创作者索取可用的日志导出方式或日志文件；取得日志前不要声称诊断已经完成。

### 5.2 使用 API 无关的日志运行骨架

下面只规定职责和顺序，不是可直接复制的 Lua 代码。实现时必须先查询当前 API 文档，再把每个“编辑器能力”替换为当前版本真实存在的类型、函数、字段和生命周期入口。

```text
配置
  客户端控件容器索引 = 创作者提供的真实索引
  预期脚本短名称 = 从创作者提供的名称或路径中归一化得到

Runtime
  状态 = NEW
  主故障是否已输出 = false
  清理栈 = 空
  启动就绪尝试中 = false
  启动就绪已尝试次数 = 0
  启动就绪重试预算 = 根据目标环境真实启动观测配置的有限正整数
  最后一次未就绪原因 = 未开始

启动事务
  状态改为 STARTING
  先验证创作者配置；缺失或格式错误立即失败
  发布完整的重试状态与重入 guard
  启用只推进 STARTING 就绪检查的回调；此时不推进玩法

每次启动就绪尝试
  通过当前 API 文档声明的能力分别取得当前脚本实例、挂载容器和挂载查询结果
  任一运行时对象暂未就绪：记录 not_ready、次数和最后原因，本次尝试结束
  达到重试预算：只输出一个聚合故障
  对象全部就绪：核对运行时短名称一致、容器查询到的实例就是当前实例
  已就绪对象身份明确不符：立即失败，不继续重试
  创建玩法资源；每次创建成功后立即登记对应清理动作
  状态改为 RUNNING
  通过当前文档声明的普通日志入口输出一次启动汇总

逐帧事务
  STARTING 时只推进一次启动就绪尝试
  仅在 RUNNING 时推进玩法
  整个事务共用一个错误边界

失败事务
  同一主故障只进入一次
  保存首个错误、阶段、状态和 traceback
  状态改为 FAILED
  停止输入、加载和逐帧逻辑
  按清理栈反向释放；清理错误只收集，不逐条打印
  生成一个带 BEGIN/END 的连续故障块
  通过当前文档声明的错误日志入口一次性输出

销毁事务
  重复调用不产生额外效果
  停止逐帧逻辑并反向执行剩余清理
  若清理失败且此前没有主故障，输出一个聚合故障块
  状态改为 DESTROYED
```

启动汇总和故障块至少包含：容器索引、预期脚本短名称、通过当前 API 取得的实际脚本名称、Runtime 状态、阶段、首个错误、traceback 和聚合后的清理错误。当前 API 文档没有提供某项运行时信息时写 `unknown`，不要虚构字段。

客户端控件容器索引只用于开工交接和诊断标识，不能与动态控件运行时 ID 或来源模板 ID 比较。脚本挂载必须使用当前 API 文档声明的脚本上下文和容器查询能力独立核对。

## 六、按以下层级调试和测试

### 6.1 验证知识与报告约束

#### 6.1.1 验证知识

| 层 | 能证明 | 不能证明 |
| --- | --- | --- |
| 静态检查 | 语法、作用域、明显 API/subtype 错误 | 编辑器真实行为 |
| 真机最小探针 | 单项编辑器约束 | 完整玩法 |
| 场景测试 | 真实交互和画面 | 所有故障分支 |
| 故障注入 | 失败收口和半初始化安全 | 正常画面保真 |

证据来源 `evidence_source`：

- `documented`：当前 API 文档明确写出。
- `provided_unverified`：创作者或已有文件提供，但尚未在真实运行环境核对。
- `observed`：已经在真实编辑器或游戏运行环境直接观察到。
- `inferred`：根据代码或静态检查推断；不能代表真机结果。
- `unknown`：没有足够证据，或现有证据互相冲突。

真机状态 `device_status`：

- `passed`：已在真实编辑器或游戏运行环境验证并通过。
- `failed`：已在真实编辑器或游戏运行环境验证并失败。
- `pending`：需要真机验证，但还没有执行。
- `not_required`：该结论不需要真机验证。

#### 6.1.2 报告约束

记录重要结论时，必须同时填写 `evidence_source` 和 `device_status`，不得把它们混成一个状态。

按下面的方式判断：

```text
API 文档已经写明，但尚未真机运行：
evidence_source=documented
device_status=pending

已经在真实运行环境验证通过：
evidence_source=observed
device_status=passed
```

`pending` 只是真机状态，不是证据来源。任何一层通过都不能替代其他层；不能把静态检查或推断写成真机通过。

### 6.2 执行静态检查

- 使用当前 API 文档声明的 Lua 版本和可用标准库，不调用未文档化或被裁剪的能力。
- 遵守当前运行环境的编译器限制；用模块表和局部作用域缩短局部变量生命期，避免单个 chunk 或函数逼近局部变量上限。
- 局部函数有前向声明，避免意外解析为全局。
- 每个控件记录当前 API 文档确认的真实 subtype，不向一种控件写入另一种控件的专用字段。
- 所有 UI 控件模板索引来自创作者交接，不存在猜测或占位值。
- 每处颜色调用都与当前文档的构造方式、调用形式、通道顺序、数值范围和 alpha 语义一致；外部设计值已显式换算，没有套用常见框架范围。
- 每个监听的注册与移除都符合当前文档；需要原回调引用时，使用注册时保存的同一引用。
- 代码中每个编辑器 API 标识都能在已确认的当前文档中找到，并且调用形式、参数、返回值、字段读写性、枚举和清理入口逐项一致。
- 启动时的配置错误、运行时 `not_ready` 和确定不匹配已经分开处理；没有因为某个生命周期回调已经发生，就把暂未取得的容器或脚本查询结果立即判为失败。
- 每项启动依赖都有独立就绪判断、统一的有限重试预算和最后原因；重试期间不创建玩法资源、不开放输入，预算内就绪只初始化一次，预算耗尽只输出一个聚合故障。
- 代码中每个跨来源数值公式、范围判断、位置比较和状态判断都有当前 含有API信息的相关文档 对数据关系的明确依据；不存在根据名称、经验、旧代码、数值外观或候选试算补出的关系。
- 坐标关系仍为 `unknown` 时，代码只使用不依赖该关系的编辑器原生命中；不存在自定义命中、绝对位置比较、输入位移驱动布局或其他猜测性坐标实现。

### 6.3 玩法完成后才进行按需真机验证

本节不是前置检验。第四节已经给出如何创建控件、绑定图片和处理输入的前置知识，AI 应直接使用这些知识实现玩法，不得把它们转换成创作者的启动前任务。

默认规则：

1. 开工接入阶段只被动核对容器/脚本挂载，并准备编辑器日志错误收口；不创建普通探针控件，不要求点击、拖动、拖拽、按键或校准。
2. 没有人工视觉或真实输入证据时，相关项记录为 `deferred_to_gameplay`，不得因此停止实现，也不得向创作者发布测试任务。
3. 只有玩法已经可玩，且创作者明确要求验收或报告图片/输入问题时，才进行针对性真机验证。优先使用已经存在的实际玩法图片、按钮和可拖对象，禁止默认创建临时图形、菱形、中心加四角、指定点击顺序或额外拖拽任务。
4. 图片实现仍必须按 4.4 使用当前 API 文档声明的资源绑定能力，并核对文档允许读回的资源状态。状态切换后是否需要重提属性由当前文档或真实证据决定。是否出现问号或缺图属于玩法画面验收；没有实际验收结果时标记为 `pending`。
5. 输入实现仍必须按 4.5 使用当前 API 文档声明的事件参数、触点身份和坐标能力，并完成事件去重和拖拽事务。只有实际玩法出现输入问题时才聚合记录事件顺序、起终点、位移和最终状态；不得把这些操作包装成开工前置任务。
6. 输入与布局之间的关系没有得到当前 含有API信息的相关文档 或专项真机证据确认时，自定义坐标命中和坐标驱动布局保持未实现；不得为了继续推进而选择一个猜测换算。
7. 多点坐标校准只能在自定义统一逻辑 HitTest 已经发生实际坐标错乱、API 文档无法解释，且创作者明确同意专项调试时使用。其他情况统一写 `multi_point_calibration=not_required`。
