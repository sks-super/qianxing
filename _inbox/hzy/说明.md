# 第 25 批 · `浮岛借木` 岛缘描边骑在格线上（岛之间保留完整一格）

> **合并目标**：**覆盖** `浮岛借木/` 的 1 个既有文件（`level.lua`）

## 1. 用户要求

`把岛屿的边框与海面上的格子线对齐，使岛与岛之间保留一格的距离，不要被岛屿的边框遮挡`

## 2. 第 24 批留下的两个副作用

第 24 批为了「外轮廓」，把沙滩带**整条外移 rim**（中心线在 `cell/2 + rim`，完全落在水面上）。代价：

- 岛的**实际占地**比一格大了 `rim`（0.17 格）→ 相邻两岛之间那条一格宽的水道，被两侧各啃掉 0.17 格，看着像「岛之间没有间隔」；
- 那条水道的**海面网格线**被压在描边底下，看不出格子了。

## 3. 改法：描边中心线 = 格子边界线

```
南北：bw = cell + rim, bh = rim,  by = cy ± cell/2      ← 中心线正好在格线上
东西：bw = rim,        bh = cell + rim, bx = cx ± cell/2
```

- **对齐网格线**：网格线本来就画在格边界（`buildSea` 里 `left + c*cell`），描边中心线压上去 → 岛的轮廓与网格线严丝合缝；
- **水道保留一格**：只往水面蹭出 `rim/2 ≈ 5 px`（cell=66 时），那一格水仍然完整、网格线看得见；
- **不是内框**：只往草地蹭 `rim/2`，看起来是草地的沙滩包边，而不是给草地套了个黄框；
- **长度给 `cell + rim`**：四条带骑线后，拐角各缺 `rim/2` 见方的一小块，两头各补 `rim/2` 正好补齐。

## 4. 配套：地面子层的顺序要换

描边骑线后**有一半压在草地边缘上**，而草地顶面是整格铺的 —— 描边必须在顶面**之上**才看得见。
所以 `ensureGroundLayers` 的创建顺序从

```
containerSide（侧面）→ containerRim（描边）→ containerTile（顶面）→ containerStump（树桩）
```

改成

```
containerSide → containerTile → containerRim → containerStump
```

⚠️ 层级 = 容器创建顺序（第 22 批定的铁律），**运行时不会重排** —— 改了顺序必须重进游戏 / 重建存档才生效。

## 5. 为什么不用「完全在格内」

那样黄边整条落在草地上（外沿 = 格线，内沿 = 格线 − rim），看着像给草地套了个内框；
用户这轮要的是「边框对齐格子线」，骑线才符合。

也考虑过「缩小草地素材让出位置」：`草地.png` 是 1024×1024、内容 bbox 900×900（四周透明），
`ART_FIT.land = 1.138` 正是为了让**内容**正好填满一格 —— 内容本身不溢出格子，
所以不存在「草皮盖住描边」的问题，也没必要动素材。

## 6. 验证

- 静态三连 + `luaparse` 12/12 + 编辑器往返全绿；
- 内核零改动 → 逐帧差分 **1 图 / 150 帧 / 0 差异**；
- 模拟器实拍沙洲群岛首屏：沙滩边压在网格线上，岛 1 与岛 2 之间那一格水完整可见、
  网格线未被遮挡；描边控件数仍是 64（几何变了、条数没变）。

层级从「一个世界容器 + 运行时排序」改成**四个固定容器**，上下关系 = 创建顺序，一次建好永不再动：

```
containerBg        海面整屏底
containerGround    ① 地面层
  ├ containerSide    水面网格 + 地块侧面
  ├ containerRim     岛缘沙滩描边
  ├ containerTile    草地顶面
  └ containerStump   树桩 / 老树根 / 接触阴影（★ 本批新增，压在顶面上、在石头下）
containerWorld     世界总层（不画东西，只当父节点 + 镜头平移对象）
  ├ containerRock    ② 石头层
  ├ containerTree    ③ 树木层（立树 / 倒木 / 木筏 / 木牌 / 倒·立过渡代理）
  └ containerPlayer  ④ 角色层（固定最上）
containerFx / containerHud / containerFade
```

- `game.createContainer(host)` 允许指定父容器；`ensureContainers` 按 石头 → 树木 → 角色 的顺序补建三个物体层 —— **创建顺序即层序**。
- **物体池按层拆开**（`state.rockCtrls` / `logCtrls` / 原 `objectCtrls` 只管树桩老根）：池里的控件建在哪一层就永远在哪一层，混池复用会把石头画到树木层去。
- 小人的立绘 / 身体 / 头 / 像素画容器 / 图元容器 / 阴影全部挂 `containerPlayer`；`restackWorld` 不再排序小人（`SUB_PLAYER` 深度键随之退役）。
- 模拟器 `selfOrderedContainers` 只标 `containerRock` / `containerTree` / `containerPlayer`。⚠️ **`containerGround` / `containerWorld` 不能标**：它们内部是固定子容器，靠模拟器按创建序归位一次即与真机一致；标了 true 模拟器跳过归位、数组原序与真机相反，首跑截图里「角色被树干盖住」就是这么来的（真机层序其实一直是对的）。

## 3. 代价（要说清楚）

角色不再参与「近处树挡住远处小人」的深度穿插 —— 小人**永远完整可见**，这是固定四层结构的必然结果，也是用户要的效果。

## 4. 验证

`SetImage(StaticReference, 100002)`**（内置椭圆图元），并在模拟器里验证通过。

**但 `100002` 只是模拟器的代理图形。** `utils.applyImage` 的注释里早就写着：
「模拟器只代理 `100001–100006` 六种基础图元，那只是代理图形，**不代表官方素材，真机不认**」。
真机上图片控件拿不到图源，`imageColor` 染色也救不回来 —— 画出来就是**一块纯白**。

- `DEFAULT_OBJ_SHADOW_ALPHA = 0` 时**连控件都不建**（建了也是隐藏的，留着只会被误开）；

为什么不再试矩形：矩形在真机上染色是好的，但它是**方的**，糊在脚下就是个方框 —— 第 19 批
用户报的「白框」就是它。既然用户要的是「删掉」，就不留了。

## 3. ② 走路时被地图盖住 / ③ 非边缘处冒出边框：同一个根因

两条其实是**同一件事**：真机上**同级控件的 `SetAsLastSibling` 排序不可靠**。

引擎的同级绘制顺序本来等于「创建顺序」，而对象池的做法是「复用旧控件、不够才新建」。
于是每到可视窗口边界（`WIN_CHUNK = 4` 格）重铺地形时：

- **新建**的控件默认排在同级最末 = **压在最上层** → 整片草地盖住小人和树（现象②）；
- 复用到的旧控件还带着上一窗的顺序，和新控件混在一起 → 侧面 / 描边压住隔壁格的草地边缘
  （现象③：岛的**内部**冒出棕色横条、米色边框）。

第 20 批的 `buildTerrain` 末尾补了 `M.restackWorld()`，就是想靠排序救回来 ——
但排序 API 本身不可靠，等于没救。

**改法：把「谁在谁上面」从运行时排序换成容器分层，层级 = 容器创建顺序。**

```
containerBg        海面（整屏底）
containerGround    ② 地形
  ├─ containerSide     水面网格 + 地块侧面（崖面）
  ├─ containerRim      岛缘沙滩描边
  └─ containerTile     草地顶面
containerWorld     ③ 物体（树/木头/石头/木牌）+ 小人
containerFx        ④ 特效
containerHud       ⑤ 界面
containerFade      ⑥ 黑幕
```

- 地形整块在物体与小人**之下**：新建多少控件都盖不住人（现象② 结构性消失）；
- 地形内部「顶面 > 描边 > 侧面」由三个子容器保证：岛内部再也冒不出边框（现象③ 结构性消失）；
- 地形绘制顺带改成**两遍**：先铺全部侧面 + 描边，再铺全部顶面 —— 就算哪天容器分层也被绕开，
  创建顺序本身也是对的。

### 代价（唯一一处）

「下一行地块挡住上一行的树」这层 2.5D 遮挡没有了 —— 地形永远在物体之下。
小人是主角，**永远可见**比这层遮挡重要，所以接受。
（每格的侧面只从**自己顶面的下沿往下**挂，永远不会伸进上一行顶面的范围，所以这个代价
只影响「树被前景地块切掉一截」，不影响地形本身。）

> **影响面**：只碰这 4 个文件。不碰 `_shared/`、`_tools/`、`伐木远征/`、`编辑器.html`、`README.md`。

> 人物脚底有白框；地图方面，岛屿上中间会出现边框，在移动时，地图的图层会改变；

## 2. ① 脚底白框：矩形阴影在真机上就是一块白

小人脚下的阴影原来是**纯色矩形**（`utils.instantiateRect`）。两个问题叠在一起：

- 纯色矩形的 `imageColor` 在真机上**缺省就是纯白** —— 一旦某个分支没填颜色，画出来就是白方块；
- 就算填对了色，矩形本身是**方的**，踩在草地上像个贴纸。

改法：阴影单独开一个池（`state.shadowCtrls` / `shadowUsed`），槽位多带一个 `image` 字段 ——
「图片」元件 `1073741870` + **内置椭圆图元 `100002`** + `imageColor` 染色，就是一枚椭圆。
颜色一律 `palette.shadowLand or "33421F"`（`or` 兜底，绝不允许 nil）；尺寸改 `DEFAULT_SHADOW_W/H`
（0.62 × 0.20 格）。**阴影池**不能和纯色矩形的 `objectCtrls` 混用（一个带图源一个不带）。

> 顺带核实（`--probe-walk` 转储 1034 条控件属性）：阴影控件类型已从 `SIM_矩形` 变成
> `SIM_图片_回退`，`color = 3233421F`（alpha 50），尺寸 `52.8 × 10.56` —— 确实生效了。

## 3. ② 岛屿中间凭空出现边框：描边的 y 用错了符号

2.5D 是**正交网格 + 厚度**，行号越大越靠**下**（屏幕 y 越小）。临水的四条边各画一条窄带，
南北两条边的 y 必须是 `cy - e[2] * cell / 2`；旧代码写的是 `+`，
于是 `e[2] = -1` 的**北**边被画到了南边、`e[2] = +1` 的**南**边被画到北边 ——
两条边对穿了整个格子，看起来就是「岛中间冒出一条条边框」。

改一个字符即可。核对方式：`--probe-walk 40` 转储出的描边控件数 = **65**，
与离线脚本 `_tmp/mexp_port/rim_probe.mjs` 按地图算出的期望条数**完全相等**。

## 4. ③ 走路时地图图层会变：换窗口那一帧漏了重排

地形按「可视窗口 + 4 格量化」重铺（第 19 批）。换窗口时**新建**的控件默认排在同级最后
—— 于是它们盖住了小人和树；而**复用**到的旧控件还保持着旧顺序。走两步就换一次窗口，
层级看着就在跳。

改法：`buildTerrain` 末尾（且**只在真的重铺了**的那一帧）调一次 `M.restackWorld()`，
按深度键 `band + row*10 + sub` 重新排一遍。O(控件数)，不是每帧跑。

> 实证：同一格「往东走 3 格再往西走 3 格」回到原地，两张截图逐像素比 ——
> 除小人（朝向变了）与底部 HUD 文字外**完全相同**（差异 bBox 全落在 y∈[300,379] 与 y≥660）。

## 5. ④ 树推倒后不留桩：树桩不是实体，是**地块属性**

原版 MExp 里 `omap` 的低 4 位是属性位：`1` 梯子 / `2` 水 / **`4` 树桩** / `8` 石头。
也就是说「这里有桩子」是**地图数据**，不是运行时生成的实体；`hmap` 里那一格的层数
**本来就已经含了桩子那一层** —— 原版 `render.js` 用 `ghat(x,y) - (stump?1:0)` 画地，
再把桩子单独画回来。所以：

- 树站着时，树干正好挡住桩子（原版 `_hasWood()` 也是这么判的）；
- 树被推倒 → 树干没了 → 桩子立刻露出来。

本批的实现：

| 环节 | 做法 |
| --- | --- |
| 载入 | `world.stumpsFromMap()` 扫 `omap` → `state.stumps`（列表）+ `state.stumpAt`（哈希 `"c:r"`），12 张图共 **144 个桩位** |
| 逻辑层 | `world.cellH(c,r)` **不动**（内核 z 全靠它，动了就和 `engine.js` 对不上） |
| 画地表 | 新增 `drawH(c,r) = cellH - (hasStump and 1 or 0)`，`groundY` 走 `drawH` |
| 画桩子 | `rebuildObjects` 新开一段：桩高恒 **1 层**（`zVis()*cell`），三层叠出圆柱感（桩身 → 竖向受光亮边 → 顶部锯口切面） |
| 隐藏 | 该格还有立着的木头（`state.trees` 里有 `type 1/2`）就不画 |

`drawH` 减掉的那一层，由桩子以 1 层高度补回来 —— 两者相加正好等于**逻辑顶面**，
所以小人踩到桩位上脚不陷、也不浮空。

> 离线核对：144 个桩位与真树（`type 2`）**逐格对位**完全吻合
> （islands 41/41、cliffs 39/39、lake 23/23…）；`foothills` 25 个桩位对 20 棵树，
> 多出的 5 个是**没有活树的纯桩** —— 原版地图里就长这样。

| 实体带整数 `z` 层号 + 高度表 `ENTH` | 同 | 小人 / 立木 / 立树 / 横木 / 竖木 / 横筏 / 竖筏 / 雪人 / 木牌 |
| 碰撞 `gect`、交互表 `EITA`/`EITB`（索引 `[actorCollision][water*8+targetCollision]`） | 同 | 交互 = 目标顶面高于可达高度 |
| 动作码 `0 停 / 1 走 / 2 推 / 3 推着走 / 4 推着爬 / 5 走两步 / 6 拒绝 / 7 交互` | `act.kind` 一一对应 | `act.interact == 8` 单独一路接住（读牌） |
| **胜利 = 站在牌子旁边按方向键，读到写着 `You win!` 的牌子** | `isGoalString()` 匹配 `You win!` / `Congratulations`（不区分大小写） | ★ 不是「走到某一格」，这条是整套改动的分水岭 |

`world.step()` 的五分支顺序（改了会立刻出现「该推的变成撞」这类怪事）：

1. 撞树 / 撞树干 → 2. 目标格能踩就踩 → 3. 踩不上且目标是倒木（同向 = 立起，异向 = 侧滑）
→ 4. 石头 → 5. 水 / 太高。

**对外接口没变**：`world.load / step / isWin / landAt / AXIS / DIRS` 照旧，
所以渲染层是**增量改造**而不是重写（`heroArt.lua`、`heroPrims.lua`、`audio.lua`、`signal.lua`、
`utils.lua`、`fadeScreen.lua` 一行没动）。

## 3. 真实地图怎么进来

新增 `浮岛借木/mexp_maps.lua`（1159 行、98 KB，**内容与 `伐木远征/mexp_maps.lua` 逐字节相同**）：
12 张图，`M.ORDER` 定顺序，每张 `{width, height, imap, hmap, omap, islands, strings}`。

> **为什么复制一份而不是共享**：客户端脚本按**模块名** `require("mexp_maps")` 解析，
> 两个游戏各自独立部署，共用一个模块要靠 `_shared/` 那种全局目录约定 —— 那是另一个话题。
> 98 KB 文本换「两个游戏互不牵连」，划算。**如果以后要收敛，这 98 KB 是唯一的重复。**

三件事：

1. `landTableFromMap(md)` → `state.land[r][c]` = **抬高层数**（`hmap` 是绝对值，不是差值），水为 `nil`；
2. `rocksFromMap(md)` → `omap` 低 4 位里 `8`（不可通行）的那些格；
3. `beginSession(md, land, rocks, name, mapKey)` 一次把整局状态摆好：`state.baseH`、`mapKey/mapName`、
   清撤销栈、复位 `wonSign / signOpen`、`state.goal = nil`。

**`hmap` 跨度极大**：`islands` 只 1~2 层，`cliffs` 0~100 层。所以：
- `state.baseH` = 整图最低层号（实际上恒为 0，因为水格是 0，等于「以水面为基准」）；
- 视觉放大系数 `zVis() = config.DEFAULT_Z_VIS = 0.15` → **1 层 ≈ 0.15 格**（对齐原版 `render.js` 的 `HZ/T ≈ 8/52`）；
- 崖面高度 `CLIFF_MAX = 2.1 格` 截断，否则 100 层 = 15 格，一块石头能顶穿屏幕。

## 4. 木牌：胜利条件换了以后必须补的东西

原版每张图都有终点牌，但**番外图那 8 张的 `You win!` 字串没有挂在任何牌上**
（`eb1=2` 的字符串没人引用）—— 这是原版数据 / 解析的既有缺陷，网页复刻同样打不通。
不修的话这 8 张图**永远赢不了**，而玩家只会觉得「撞在一块牌子上没反应」。

修法（`world.lua` 的 `buildSignIdx`）：

- 建一张覆盖表 `state.signIdx[tostring(isl)..":"..tostring(num)] = 第几块牌`；
- 如果整张图**没有任何一块牌**的字符串是通关语 → 把那条没被引用的 `You win!` 挂到
  **离出生点最远**的那块牌上（直觉上那儿就是终点）；
- ⚠️ **不改 `ebIsl`**：改了会让「与已验收内核逐帧差分」出现假差异。

配套：

- `config.MAP_THEMES` + `config.PALETTE_SNOW` / `PALETTE_DIGRESSION`：`icy-lake` / `cliffs` /
  `caustic-bluff` 走雪原，8 张番外图压暗；
- `config.SIGN_TEXTS`：12 张图**全部牌子**的中文译文（38 条），含 8 枚碎片密码
  `CC5Y / 58LQ / LZQ3 / 5LDM / WDE5 / FA5Y / SFTB / HXQR` 与 4 条主线长串；
- `game.lua` 的木牌面板（底 + 正文 + 页码三件套）：**空格翻页**，最后一页再按一次关掉；
- HUD 从「第 0N 关 · 步骤」变成「**图名（i/12）· 步数 N · 碎片 n/8**」，通关后追加「（已通关）」。

## 5. 渲染要跟着改的三处

真实地图带来的不是「换个素材」，是三个结构性问题：

### 5.1 深度排序：从「两张全局趟」改成「按行交错」

老版是「先铺满装饰、再统一盖顶面」，靠「相邻顶面盖住描边」让描边只露在岛缘。
地块一旦有高差，**崖面会被远处一行的顶面整片盖掉**（崖面永远看不见）。

现在同一行内按 sub 从小到大：`侧面 0.1 → 临水描边 0.4 → 顶面 0.6`，
物体层 `BAND_OBJ = 1005`、`sub/10` 压进 (0,1)，于是「行号越大越晚画」天然成立。

### 5.2 地形窗口化

真实地图最大 **72×26 = 1872 格**，一次铺满会造上千条控件（真机扛不住）。
现在只铺「当前看得见的那一窗」：

- 窗口 = 小人 ± 半屏 + 2 格余量，再按 **4 格块量化**（`WIN_CHUNK` / `WIN_MARGIN`）；
- 镜头把小人钉在屏幕中央 → 换窗只可能发生在块边界，而且**窗口比屏幕大几格**，
  重铺发生在屏幕之外，看不见跳变；
- 逐帧判定只是一次字符串比较（`state.terrainWinKey`），代价可忽略；
- 海面底 + 水网格单独由 `buildSea()` 管，**整屏一块**，不受窗口影响。

### 5.3 新画法

- **木筏**（两根木头叠出来的）：主木顺着躺向 + 一根横的短木压在上面 + 亮边 ——
  必须和单根木头**一眼分得开**，否则玩家不知道「这已经能撑了」；
- **木牌**：柱 + 板 + 两道「字迹」；终点牌的板子换成金色，顶上再插一面小旗，
  让玩家在很远的地方就认出「那块就是要读的」；
- 树根恒空（新规则下不再产生树根），代码保留只是为了兼容老存档。

# 第 18 批 · 新游戏 `伐木远征/`：把网页版 MExp 整套搬成千星客户端 Lua

> **提交**：`bdeb92a`（`伐木远征/` 8 个 `.lua` + 1 个 `README.md`，**全部新增**）
> **合并目标**：仓库根新建 `伐木远征/`（与 `浮岛借木/`、`TickHop/` 同级）
> **影响面**：**零**。不碰 `_shared/`、不碰 `_tools/`、不碰任何既有游戏。

## 1. 起因

用户手上有一个已经做完的网页游戏「伐木远征 · MExp 复刻」
（`怪兽远征/MExp复刻`：canvas + `engine.js` 纯逻辑 + `render.js` 程序化 2.5D + 12 张从
`.8xv` 世界文件解出来的地图），要求**整套转成能在千星奇域里跑的 Lua 脚本**，
替换原先那套脚本。

原版是 TI-83/84 计算器上的黑白解谜游戏 **MExp**（*A Monster's Expedition* 的极简版）：
推木、滚木、搭筏渡水，从沙洲一路走到雪山顶。

## 2. 拆成四层

| 文件 | 行数 | 职责 |
|---|---:|---|
| `mexp_engine.lua` | 692 | ★ 纯逻辑：`World` + `mven` 状态机、快照回滚 |
| `mexp_maps.lua` | 1160 | 12 张地图数据（由 `maps.js` 逐字节生成） |
| `mexp_render.lua` | 614 | 2.5D：窗口铺砖、崖面、实体池、镜头平移 |
| `mexp_ui.lua` | 286 | 标题 / 选关 12 卡 / 弹窗 8 行翻页 / 上下信息条 |
| `game.lua` | 563 | 入口：参数、4 层容器、按键、走一步、撤销、重置岛、切屏 |
| `config.lua` / `state.lua` / `utils.lua` | 182 / 90 / 243 | 真源 / 字段声明 / 控件与颜色封装 |

**没有二进制素材、不需要图库 ID** —— 全部图形是纯色矩形 + 内置圆盘图元 `100002`。

## 3. 凭什么说「玩法没跑偏」（本批最重要的部分）

网页版的 `engine.js` 是纯函数式的，于是做了一套**逐帧差分对照**：

- 用 **fengari**（纯 JS 的 Lua 5.3 VM）在 Node 里跑本工程的 `.lua`，
  同时用 `vm` 跑原版 `engine.js`；
- 同一份输入喂两边：`Mdx,dy` 移动、`Tx,y,z` 随机瞬移（每 11 步一次，专门踩边角）、
  `R` 重置岛、`U` 回滚、`E` 导出 `emap`；
- **每一帧**比对：每个实体的 9 个字段（`x/y/z/type/ebIsl/ebNum/mven/layers/props` 等）
  + `emap` 全格字符串 + `IT/IP/lastT`。

结果：

| 轮次 | 规模 | 结果 |
|---|---|---|
| 早前一轮 | 18 个世界 × 24 序列 × 60 步 | **55 568 帧，0 处不同** |
| 本轮定稿 | 18 个世界 × 10 序列 × 60 步 | **23 127 帧，0 处不同** |
| 收尾回归 | 18 个世界 × 6 序列 × 50 步 | **11 592 帧，0 处不同** |

（18 = 12 张正式地图 + 6 张原版自带的自检世界。）

这套对照抓到过一个**真 bug**，很值得记：
`resetIsland()` 在 JS 里是 `[...entities]` 拷一份再逐个 `removeEnt`，
Lua 版一开始图省事用「过滤保留」，结果 **`emap` 的归属没更新**，
表现是重置后某一格 `JS=0 Lua=1`。改成先拷贝再 `self:removeEnt(e)` 才对。

## 4. 渲染怎么搭（决定性能的三个选择）

1. **水不画控件**：整屏一块底色矩形。原版逐格画水 + 涟漪线，一屏 240 格水，
   一格一个控件不划算。
2. **地形按「可视窗口」铺**：只铺镜头看得见的那 20×12 格，**跨格才重铺**
   （`state.winKey` 变了才重建），格内位移交给容器平移 → 每帧 O(1)。
3. **实体池**：一个 1×1 容器 + 最多 8 个子图元（影子 / 身体 / 耳朵 / 眼睛 / 脚…），
   **按签名重画**（`type|isl|num|look`），签名不变就只挪容器。

观感上专门补了两笔，不然「原版感」会差很多：

- **砖缝**：同色同高的一整段先铺一层 `theme.edge`，再把每格内缩 1.4px 的顶面压上去 →
  格子之间自然露出 2.8px 的缝；
- **逐格明暗抖动** ±3.5%（原版 `shade(base,(hash2-0.5)*0.07)`），没有它就是一大块死板的地。

## 5. 镜头那个坑（三个地方必须同一套坐标约定）

`M.focus()` 返回**屏幕正中那一点的世界坐标**（`camX`,`camY`），容器位置 = `(-camX, -camY)`。
世界坐标是 **y 向上**的（行号越大 y 越负），所以 `camY` 是负数、容器要往上抬。

- `focus()` / `applyCamera()` / 实体剔除 —— **三处必须一致**；
- 把 `camX` 当左上角 → 表现是「左半屏空、地砖跑到右边」；
- `camY` 符号写反 → 表现是「整屏只剩水」。

拼这套时踩了两次，都是靠临时在 `OnUpdate` 里打 `cam / worldPos / children` 才定位到。

## 6. 上真机（模拟器）后才暴露的三个问题

| 症状 | 根因 | 改法 |

# 第 17 批 · 把四肢拆成「部件 + 关节」，走路时腿会迈步

## 1. 起因

需求原话：**「把人物的双手以及双腿这些关节拟合出来，在移动过程中为角色添加双腿的移动动作」**。

第 16 批把 292 个椭圆平铺成一个整体，移动时整幅画平移 —— 看上去是「滑行」。
这一批要把椭圆按身体部位分成零件，找出关节，走路时让腿和手臂各自绕关节动。

## 2. 怎么分部件（离线，`_tmp/primitive_opt/gen_hero_parts.py`）

椭圆数据只有「位置 + 大小 + 角度 + 颜色」，没有语义。用**归一化位置**切：

| 部件 | 判据（x 相对人物竖中线，y 0=脚底 1=头顶） | 关节（轴心） |
|---|---|---|
| head 头 | `y ≥ 0.60` | (0, 0.60) |
| torso 躯干 | `0.24 ≤ y < 0.60` 且 `|x| < 0.15` | (0, 0.40) |
| armL / armR | `0.24 ≤ y < 0.60` 且 `|x| ≥ 0.15` | (∓0.165, 0.585) 肩 |
| legL / legR | `y < 0.24`，按 x 正负分左右 | (∓0.07, 0.255) 髋 |

- ★ **腿只取「脚踝以下」**：这个角色穿长裙，把整段下半身当腿去旋转，裙子会从腰上撕成两半；
  只把裙摆下沿和脚当腿，摆动时剪影不裂。
- ★ **手臂图元不参与裁剪**：手臂又细又小，按「视觉权重」裁会被整段删掉，摆臂就看不出来了——
  生成器里对手臂打了保护标记。
- 各视角结果：正面 351（头83/躯干111/左臂45/右臂42/左腿28/右腿42）、背面 261、右侧 197、左侧 196。

## 3. 运行时结构

```
heroPrBox            整幅画（每帧只移动它，含走路起伏）
 ├─ head   容器     中心=头关节（不转）
 ├─ torso  容器     中心=躯干关节（不转）
 ├─ armL/armR 容器   中心=肩关节 → 绕 Z 旋转 = 摆臂
 └─ legL/legR 容器   中心=髋关节 → 位移 = 迈步 + 抬脚（另加一点点转角）
```

- 每个部件一个控件池 + 固定的父子关系：换视角只改属性，不新建、不搬家。
- 数据格式改成 `{pivotX, pivotY, n, 然后 n × {x,y,w,h,rot,rgb,alpha}}`，
  `x,y` 已经是**相对关节**的偏移 —— 容器一转，整组就绕着关节走。

## 4. 动作怎么做

| 动作 | 实现 | 默认值 |
|---|---|---|
| 迈步 | 两条腿反相前后位移 | ±0.030 格 |
| 抬脚 | 前摆那条腿离地 | 0.030 格 |
| 摆腿 | 髋关节小角度旋转 | 9° |
| 摆臂 | 肩关节旋转，**与腿反相** | 13° |
| 重心起伏 | 整幅画上下浮动（一个步幅两次） | 0.012 格 |
| 周期 | 固定 0.3 秒一个来回，**与单步动画(0.1s)解耦** | `DEFAULT_HERO_WALK_PERIOD` |

- ★ **为什么周期不绑单步**：一步只有 0.1 秒 ≈ 3 帧（模拟器 30fps），绑在一步上只会看到闪烁。
- ★ **起步渐入 / 停下渐出**：`heroWalkAmp` 0~1 包络，松开方向键两帧内淡出，腿不会「啪」地弹回。

## 5. 踩过的两个坑（都是「画面上明显不对」）

| 坑 | 现象 | 根因 | 改法 |
|---|---|---|---|
| 部件容器尺寸设成了 1 格 | 一摆臂/摆腿，整块零件被甩到身体外十几像素 | 容器的旋转原点跟自身尺寸挂钩，尺寸一大就绕「左上角」转 | 部件容器**保持 1×1**，旋转原点误差变成亚像素 |

## 8. 修正：静止时「裙子敞开」（当天用户反馈）

**验证**：修复前后静止帧对比 —— 修复后蓝裙子盖住白衬裙、脸部/靴子恢复清晰，与原画同尺度对照一致；
走动帧仍是侧身迈步、幅度很轻。

`{kind, cx, cy, w, h, rotZ, 色号, alpha}` 逐层叠加）。上一轮已经把「正面」那份从 1200 裁到 1078
（按全分辨率判据），这一轮是要**真的当主角用**。

## 2. 为什么不能原样照搬 1200 个

1. **1200 个控件只画一个小人**，再加世界本身 500 多个控件 —— 真机大概率跑不动；
2. 缩到游戏内 **1 格 = 68px** 之后，大量椭圆不足 1 个屏幕像素，画了也看不见；
3. 导出脚本自己的定位公式 `py = (cy - IMG_HEIGHT/2) * scale` 与数据坐标系（`cy` = 行号取负）**差一整幅画布高**（1536px），图形会整体偏移。

## 3. 做法

```
四张立绘 → 工具箱导出四视角脚本（1200 椭圆/视角，1024×1536）
        │ ① 等比缩到 1 格：scale = 68 / 内容高度(实测 1324~1348 → 统一 1344)
        │ ② 按 **68px 尺度**裁冗余（判据算在缩略图上，不是原图）
        ▼
浮岛借木/heroPrims.lua   { x, y, w, h, rot, rgb, alpha }，单位「格」，y=0 = 脚底线
        │ ③ level.lua：repaintHeroPrims() / placeHeroPrims()
        ▼
292 / 208 / 188 / 182 个控件（正面/背面/右侧/左侧），画在 heroPrBox 容器里
```

- **裁多少**：1200 → **292（正面）/ 208 / 188 / 182**，即 **-76% ~ -85%**；
  在 68px 图上裁前裁后 **PSNR 36~37dB**（该尺寸肉眼无差）。工具：`_tmp/primitive_opt/gen_hero_prims.py`。
- **每笔怎么画**：`图片`元件 `1073741870` + `SetImage(StaticReference, 100002)`（**引擎内置椭圆图元**）
  + `imageColor` 染色 + `SetLocalRotation(0,0,rot)`。`100001/100002/100003` = 矩形/椭圆/三角形，
  任何工程都能用 —— 所以这条路**完全不需要图库、不需要上传图片**。
- **摆位**：容器中心 = 脚线 + 半格，子控件 `y − 0.5` → 整幅画正好 1 格高、底边压脚线。
- **转身**：换一套椭圆重摆。四视角笔画数不同 → 池按最多的建，少的视角把多余控件**藏起来**（不销毁）。
- **每帧只移动容器**（`placeHeroPrims`），292 个子控件一动不动。
- **优先级**：图元笔触 > 图片立绘（填了图库 ID）> 像素画 > 人物素材 > 纯色。任一门失败当场回退。

# 第 14 批 · 世界放大一倍 + 镜头跟随（人物钉在屏幕中央）

## 1. 起因

需求原话：**「把角色，地图和其他所有物品放大一倍，若一个屏幕无法放下整张地图时，
角色移动时镜头视角跟着移动相同距离，以展示未显示的地图，保证人物始终在屏幕中央」**。

## 2. 为什么只需要改一个数

这套工程里**所有尺寸都是 `state.cellSize` 的函数**：
地块边长、岛缘描边、厚度侧面、树高、石头、终点旗、涟漪、扬尘、脚线偏移、
小人像素块（`cellSize / ROWS`，所以恒 1 格高且不变形）……

于是「放大一倍」不需要碰任何美术尺寸、不需要改任何形状，只要让
`computeGeometry()` 算出来的格子边长乘 2：

```lua
base = 整张地图塞满一屏时的边长     -- 原来那套算法，zoom = 1 时就是它
cell = base × state.viewZoom        -- 真正用的边长
```

实测（1280×720，22 列 × 13 行，扣掉上下信息条后可用 1280×522）：

| | 改之前 | 改之后 |
|---|---|---|
| `base` / 实际 `cell` | 34 / **34** | 34 / **68** |
| 整张地图（含岛缘描边） | 760 × 464 | **1519 × 927** |
| 一屏放得下吗 | 放得下（所以镜头不用动） | **放不下 → 镜头跟随** |
| 小人高度 | 34 px | **68 px** |
| 小人像素块边长 | 1.21 px | **2.43 px**（顺带更清晰了） |

> ⚠️ **上限必须拆成两条**：`DEFAULT_CELL_MAX = 64` 仍然是「整图一屏」的上限，
> 放大后走 `DEFAULT_CELL_MAX_ZOOM = 176`。共用一条的话 `64 × 2` 会被同一个
> `clamp` 压回 64 —— 放大**静默失效**，画面上只是「看着没变大」，日志也不会报错。

## 3. 镜头怎么跟：平移「世界容器」，不是重算每个控件

```lua
containerWorld:SetAnchoredPosition(camX, camY)   -- 地形 + 物体 + 小人，一次搞定
containerFx:SetAnchoredPosition(camX, camY)      -- 涟漪 / 扬尘用同一套世界坐标
```

- **为什么能这么干**：容器是 `anchor 0.5 / pivot 0.5 / size 1×1 / 位置 (0,0)`，
  子控件也都是 anchor 0.5 —— 于是「子节点的 `anchoredPosition`」就等于「世界坐标」，
  平移容器 = 平移整个世界，**O(1)**。地形 + 物体 + 小人一共几百个控件，
  逐帧重算坐标会变成几百次 `SetAnchoredPosition`，必然掉帧。
- **先验证再动手**：改代码之前先做了一次单点实验 —— 只把 `containerWorld`
  平移 137px，截图量草地包围盒：x 重心 `619.2 → 755.9`，**正好 +136.7px**。
  证明「平移容器会带动全部世界控件」这条前提成立，方案才落地。
- **bg / hud 不动**：海面要铺满整屏，HUD 要钉在界面上。
- **fx 必须一起动**：涟漪 / 扬尘是同一套世界坐标，只动 world 会让特效留在原地
  （小人走了、脚下的水花还在原处）。

## 4. 小人为什么「钉」在中央

```lua
camX = -playerVisX                                -- 小人世界 x + camX = 0 = 画布中心
camY =  viewCenterY - (playerVisY + cell * 0.5)   -- 小人「身体中心」落在可视区中心
```

- `viewCenterY` = HUD 下沿与底部信息条上沿的中点（1280×720 下是 `+25`），
  不是画布正中心 —— 否则人物会被顶到信息条里。
- 相机用的是**刚补间完的** `playerVisX/Y`，与小人位移同一条 `smoothstep` 曲线、
  同一帧，所以位移过程中小人在屏幕上**一动不动**，滑动的是整张地图。
- **顺序不能反**：先更新小人位姿、再 `updateCamera()`。反了会慢一帧，走起来画面发抖。
- 换关 / 重开 / 第一帧走 `snapCamera()`（直接吸附，不做补间），
  否则画面会从上一关的位置滑进来。
- `DEFAULT_CAM_FOLLOW = 1.0` 是「完全同步」。想要「人物先从中央漂出一点、再回中」的
  手感就调成 `0.85` 左右（`camX = lerp(camX, tx, follow)`），但那样就不是严格居中了。

## 5. 顺带必须补的三处（放大后才暴露的问题）

1. **顶部信息条原来只有 `alpha 130`** → 地图顶到 HUD 后面，树冠 / 草地会从关卡名背后
   透出来，深绿块和白字叠在一起。`DEFAULT_HUD_ALPHA` 改 **230**（实测 200 还会透出树冠 / 石头的深色斑块，230 只剩约 10% 透出，字面干净）。
2. **底部原来根本没有底色** → 消息行与三行提示直接压在草地上。新增 `state.hudBottomBar`
   （与顶部同款同色，高 = `DEFAULT_HUD_BOTTOM_RESERVE`）。
3. **水面网格只铺到地图外 8 格** → 放大后镜头一移，屏幕边缘就会露出「有网格 / 没网格」的
   硬边界。改成按屏幕算：`over = ceil(画布宽 / cell / 2) + 2`（竖直方向永远更小）。
   控件只多十几条（网格线总数 69 → 85），可忽略。

# 第 12 批 · 小人更清晰、更贴原图：调色板去重 + 网格回到 28 行

## 1. 起因

需求原话：**「让小人变得更清晰，且更接近我给你的图片中展示的样子」**。

第 8 批把四张立绘压成像素画时选了 `ROWS = 32` / 12 色，画面里小人是一团偏白的块，
五官和头冠都读不出来。

## 2. 排查：先量屏幕，再决定改什么

实测 1280×720 下小人非草像素 bbox = **约 52 × 54 px**（1 格高）。这条数字改变了一切：

- 32 行 → 每块 ≈ 1.7 屏像素；40 行 → 1.35；48 行 → 1.13。
- **每块不足 2 个屏幕像素时，引擎的抗锯齿会把相邻块糊成一片**，
  于是「加密」不但没用，画面上反而**更糊**（32 / 40 / 48 三版在游戏里几乎分不出来，
  28 行那版反而最「利」）。

结论：清晰度的瓶颈不在网格精度，而在**颜色预算**。

## 3. 真正的根因：12 个调色板里有 5 个是「同一个白」

`k-means` 只看 RGB 距离，角色整身浅色 → 它把 `#F5F8FB`、`#F3F6FA`、`#EEF2F7`、
`#E0E6F1` 这些**肉眼完全同一个白**各占一格。结果是：

- 10 个名额用来描述「白 + 灰」，**蓝色头冠、蓝眼睛、裙摆青蓝只剩 2 个名额**；
- 白色之间那点差异在 1 格像素上根本看不出来，纯属浪费。

## 4. 改法（两个文件 + 一个工具参数）

| 改动 | 位置 | 说明 |
|---|---|---|
| **调色板去重** `--pal-dedupe 24` | `_tools/make_hero_pixels.py` | k-means 之后把「距离 < 24 的两个色」并成一个（加权平均），再按亮度重排。**20 → 13 色**，省下的名额自动还给了有色相的颜色 |
| 网格 `ROWS = 28` / `COLS = 17` | 同上（`--rows 28`） | 每块 ≈ 2 屏像素，边缘不再被糊平 |
| 内置数据重生成 | `_tools/emit_hero_builtin.py` | 字符表 `0123456789ab` → `0123456789a…v`（最多 32 色），`--write` 重写 `level.lua` 的 `HERO_BUILTIN` 段 |
| 版本戳 `b11` → `b12` | `level.lua` | 真机日志能分辨用没用上新文件 |

顺带把生成器做成**全参数化**（`--k / --pal-dedupe / --dark-share / --denoise / --cover /
--merge-tol / --out / --preview`），以后调小人不用改代码。

**块数反而少了**：187 → **146**（正面），控件压力更小。

## 5. 验证

| 项 | 结果 |
|---|---|
| 静态三连 | blocks=0 / refs=0 / scope=0 |
| 模拟器挂载 | `mountError: null`、`版本 level=b12 \| heroArt 脚本=有` |
| 自检日志 | `小人=像素画 \| 像素块=146 \| 数据源=heroArt 模块 \| 原因=无` |
| 画面 | 32 / 40 / 28 三版同机位截图对比，28 行版轮廓最利、头冠与裙摆层次可辨 |
| 玩法 | **零改动**：`world.lua` / `config.lua` / `编辑器.html` 都没碰，三关最短解仍 14/14/14 |

## 6. 教训（已写进 README §2.5）

- **先量屏幕像素，再谈分辨率**。角色只有 54 px 高时，`ROWS > 30` 的收益是负的。
- **k-means 的 k 不等于「有效颜色数」**。浅色主题下必须去重，否则颜色预算被近白吃光。
- 想让人物真正「变大变清楚」，只能改玩法尺度（格子大小），不是改 `ROWS`。

# 第 10 批 · 「还是橙色块」的真正原因：真机面板没填的参数返回 **0**，把默认开的东西全关了

## 1. 起因

> 画面是仍是橙色块，请查清原因，并做修改

## 2. 先定位「橙色块」是哪条分支

`buildPlayer` 只有三条路：

| 分支 | 条件 | 小人长什么样 |
|---|---|---|
| **像素画** | `state.heroPixel` 为真 | 187 块纯色矩形拼的人 |
| **立绘** | `state.playerCtrlArt` 为真 | 「人物」素材元件自带立绘 |
| **纯色回退** | 以上都不成立 | **`F2A03C` 橙色身体矩形 + `3A2A20` 深色头** |

`config.DEFAULT_PALETTE.playerBody = "F2A03C"` —— **正是用户描述的橙色**。
所以橙色块 ⇒ 走的是第三条 ⇒ `heroPixel` 与 `playerCtrlArt` **同时为假**。

## 3. 根因：`getParamNumber` 的默认值挡不住「数字 0」

原代码：

```lua
function getParamNumber(name, default)
    local v = script:GetParam(name)
    if type(v) == "number" then return v end   -- ← 0 也是 number，原样返回
    ...
    return default                              -- ← 只有"非数字"才用默认
end
```

**真机脚本参数面板里，没填的数字参数返回 `0`（不是 `nil`）。**
`type(0) == "number"` → 直接返回 0，于是：

```lua
state.useArt     = (getParamNumber("useArt", 1) or 0) > 0        -- 0 > 0 = false
state.heroPixelOn = (getParamNumber("heroPixelOn", 1) or 0) > 0  -- false
state.view25d     = (getParamNumber("view25d", 1) or 0) > 0      -- false
```

四个「默认开」的开关在**没配参数的真机上集体变 false**。后果和用户看到的现象逐条对上：

| 开关被误关 | 表现 |
|---|---|
| `useArt = false` | 海水 / 草地 / 树木 / **人物**全部退回纯色矩形 → 小人变橙块 |
| `heroPixelOn = false` | 像素画根本不画 |
| `view25d = false` | 岛没有厚度侧面（平面视角） |

这也解释了为什么第 7 批（`SetImage` 换立绘）同样"看起来没生效"：那条路也要求
`playerCtrlArt = true`，而它同样被 `useArt = false` 挡住了 —— **问题不在小人，在参数**。

> ★ 这条根因同样解释了「元件索引」那一类：`containerPrefabId / playerPrefabId` 等
> 读到 0 时，容器与素材控件全走回退，所以画面"能跑但全是纯色"。

## 4. 改法：`0` 视为「没配」，关闭改成 `-1`

`game.lua` 新增两个 helper，所有读取点统一走它们：

```lua
local function paramSwitch(name, dflt)   -- 开关：nil / 0 → 用 dflt；>0 开；<0 关
local function paramId(name, dflt)       -- 索引：nil / <=0 → 用 dflt
```

- 覆盖：`containerPrefabId` `rectPrefabId` `imagePrefabId` `textPrefabId`
  `water/land/tree/playerPrefabId` + `useArt` `heroPixelOn` `view25d` `waterGridLines`
- **`rectImageId` 不动**：它的 `0` 是有效值（= 不改图源）
- 音效 ID 不动：`0` = 无音效

### ⚠️ 约定变更（使用方必须知道）

| 参数 | 旧 | 新 |
|---|---|---|
| `useArt` | `0` = 关 | **`0` / 空 = 没配（= 开）**；**`-1` = 关** |
| `heroPixelOn` | `0` = 退回立绘 | **`-1` = 退回立绘** |
| `view25d` | `0` = 平面 | **`-1` = 平面** |
| `waterGridLines` | `0` = 旧棋盘 | **`-1` = 旧棋盘** |

## 5. 新增「参数快照」日志（和上一批的自检配成一对）

```
[浮岛借木] 参数 useArt=true heroPixelOn=true view25d=true | 元件 rect=1073741894 container=1073741876 player=1073741886

# 第 9 批 · 「像素小人没显示」：真机兜底 + 一行自检（不改玩法、不改画面）

## 1. 起因

> 为什么我把 lua 脚本导入后，像素小人没有显示出来

## 2. 结论：不是「画错了」，是**四道门静默回退**了

像素画是**可选表现层**。第 8 批为了「一个表现层不许把整关拖崩」，把失败全做成了
静默回退 —— 好处是不会因为一个表现层把整关拖崩，**代价是它不报错，只安静地变回老样子**，
从画面上根本看不出断在哪。

`buildPlayer` 里按顺序有四道门，任何一道没过都会回退：

| # | 门 | 断了画面会怎样 | 真机上最常见的触发 |
|---|---|---|---|
| 1 | `require("heroArt")` 成功且是 table | 退回立绘（**有**小人） | **`heroArt.lua` 没导入** —— 第 8 批唯一**新增**的脚本，编辑器里要单独新建同名脚本 |
| 2 | `heroPixelOn > 0` | 退回立绘（**有**小人） | 脚本参数面板里的旧值 `0` 覆盖了 `config` 的默认值 `1` |
| 3 | `ensureHeroBox()` 拿到画布容器 | 退回立绘（**有**小人） | `containerPrefabId = 0`（见 §3 缺陷 A） |
| 4 | `repaintPlayerArt()` 真画出来了 | **小人凭空消失** | 真机控件数超限，一块都没建出来（见 §3 缺陷 B） |

所以「没显示」有两种完全不同的样子，**先看画面里还有没有人**：
还有小人（只是变成老立绘 / 橙色块）→ 第 1～3 道门；连人都没了 → 第 4 道门。

## 3. 顺着这次反馈修掉的两个**真实缺陷**（代码里的不对称，不是猜的）

### 缺陷 A：画布容器**没有回退**，全世界只有它搞特殊

`game.lua` 的 `createContainer()` 一直是**两级回退**（容器节点 → 矩形全透明），
但第 8 批新写的 `ensureHeroBox()` 写的是 `if cid <= 0 then return false end` ——
**容器节点拿不到就直接放弃像素画**。

而 `containerPrefabId` 恰恰是「脚本参数面板留空 / 老存档没登记」时最容易变成 `0` 的那一项。
偏偏这时**世界容器自己已经回退成功了**，画面一切正常，只有小人悄悄变回立绘 ——
这是最难查的一类：什么都不报，只有一处表现层不对。

→ 现在 `ensureHeroBox()` 与 `createContainer()` **同源**：拿不到容器节点就退回
「矩形 + 全透明」当坐标系宿主（容器只是个坐标系，看不见也不影响）。

### 缺陷 B：像素块**一块都没建出来**时，小人会蒸发

第 8 批的顺序是「先隐藏立绘 → 再画像素」，但 `buildPlayer` **不看
`repaintPlayerArt()` 的返回值**。真机控件数逼近上限时 `poolGet` 全部返回 nil，
187 块一块也没画成 → **立绘已隐藏 + 像素块 = 0 = 小人没了**，比回退立绘糟得多。

→ `repaintPlayerArt()` 现在会**主动认输**：

- 连续 8 块创建失败就停（不在真机上白试一百多次）；
- 画出来的块数 **< 总块数的一半** → 清池、隐藏画布、`return false`。

→ `buildPlayer` 收到 `false` 就把 `heroPixel` 降回 false，**走立绘分支**。
一句话：宁可显示老立绘，也绝不留一个空白。

## 4. 新增：启动时打一行自检

```

- 原因同时留在 `state.heroPixelWhy`，**没有日志面板也能靠「小人是什么形态」反推**。

## 3. 数据从哪来：`_tools/make_hero_pixels.py` → `heroArt.lua`

四张立绘 → 12 色调色板 + 网格上的矩形表。**五个关键工艺**（每一步都为一个具体问题）：

1. **四张一起聚类**出调色板 —— 分开聚类的话，转身时头发会从银白跳到灰白。
2. **肤色锚色钉死** `#F2D8C4` —— 角色整身都是浅色，k-means 会把「暖白皮肤」并进
   「冷白裙」，脸就和头发糊成一团（试过，糊得认不出）。
3. **每格取众数、不取平均** —— 平均会把深色描边和瞳孔一起抹淡。
4. **暗色优先**：格内暗像素占比 ≥16% 就改用「暗像素的众数」—— 决定「能不能看出五官」。
5. **3×3 众数滤波 + 贪心矩形合并**（行 RLE → 向下合并同色同宽）——
   控件数从「像素数」压到「色块数」：一格裙摆是一块矩形，不是二十个小方块。

产物：`COLS=20 × ROWS=32` 的网格、12 色、四向各 **160~190 块**矩形。

## 4. 运行时怎么画（`level.lua`）

```
素材/*.png ──make_hero_pixels.py──▶ heroArt.lua ──repaintPlayerArt()──▶ 矩形池
                                                                    │
                                              heroArtBox（容器，每帧只移动它）
```

- 一块的边长 = `cellSize / ROWS` → 角色**恒 1 格高**，格子怎么自适应都不变形（像素恒正方）。
- 网格坐标（左上原点、y 向下）→ 容器坐标（中心原点、y 向上），画布**底边压在脚线上**。
- 换朝向 = `setPlayerFacing()` → `repaintPlayerArt()`：**重画一套矩形**，不新建控件（走对象池）。
- 每块往外扩 `0.1 格像素`：亚像素矩形挨着摆，真机会在缝里露出底色（一条条亮线）。

**为什么装一个容器**：小人每帧都在动。若每块各自 `SetAnchoredPosition`，一帧几十次调用；
装进 `heroArtBox` 后每帧只移动 1 个控件，像素块坐标一次算死。
容器挂在 `containerWorld` 里并参与 `restackWorld()`（`SUB_PLAYER`），
所以「前面的树挡住后面的小人」仍然成立。

## ③ 为什么是「换图」而不是「转角度」

千星没有「把立绘转到 45°」这种能力，`rotationZ` 转出来是歪的（正交 2D 立绘转了就穿帮）。  
四张同角度立绘 + 换图是唯一能做出「转身」的路子。

代价是**四张必须同画布、同留白**（本工程都是 1024×1536 原图 → 存 512×768），  
尺寸统一交给一套系数，**不许逐张调**：

```
DEFAULT_ART_FIT.player = { w = 0.751, h = 1.126, dy = 0.508 }
   w / h = 0.6667 = 1024 / 1536（必须严格相等，否则立绘被拉变形）
   内容高 1364 / 1536 = 0.888  →  1 / 0.888 = 1.126（内容正好 1 格高）
   内容底边 1461 − 画布中心 768 = 693 / 1536 × 1.126 = 0.508（脚踩在脚线上）
```

（旧的 `人物.png` 是 1024×1024 的单图、系数 1.707；换成 2:3 画布后必须重算，  
**手调一定会出错**，所以 `_tmp/make_hero_art.py` 里是抠完图自动反算并打印的。）

## ④ 抠图：为什么不能「近白就透明」

四张是 **JPG 白底**，直接当图源 = 游戏里一个白方块。但角色本身大量纯白（银发、白裙蕾丝），  
用「所有近白都变透明」的阈值法会把头发和裙子打穿。

所以只从**画布边缘**做 flood fill（4 个种子点，thresh 26），**与边缘连通的近白**才算背景；  
角色内部的白不连通边缘 → 一定保得住。再用 3×3 最小值滤波把 alpha 边界向内收 1px，  
去掉 JPG 抗锯齿留下的那圈白边。

产物：512×768 透明 PNG，四张合计 ~1.5 MB（原图 4.6 MB，游戏里一格只有 34–44 px，  
留 10 倍余量纯属浪费）。

## ⑤ 白框（涟漪）为什么直接关掉

涟漪是**一块纯白矩形** —— 图元只有矩形，画不出圆。它铺在小人脚下，真机上看起来就是  
「脚下一个白框」，把草地和角色的脚一起糊住。

## 3. 核心：同一根木头的「两个姿态」

第 5 批已经把「立着的也是一根**无叶树干**」这件事在**规则层**做对了（`tree.bare` 标记）。  
本批解决的是**表现层**：光「没有树叶」还不够，玩家一眼扫过去还是容易把两者看成一回事。

所以给同一根木头立了**两套完全不同的形状 + 配色语言**，四个维度同时拉开：

| 维度     | 躺着的木头                                               | 立起来的树干                                                                  |
| ------ | --------------------------------------------------- | ----------------------------------------------------------------------- |
| **剪影** | 长而扁 `1.00 × 0.50` 格（横着一段）                           | 窄而高 `0.36 × 1.00` 格（竖着一截）                                               |
| **明暗** | 暗一档的旧木色 `logSide 9C6C36` + **贴地暗边** → 「躺在地上的旧木头」    | 亮一档的新木色 `logStandSide AB7A3E` + **根部土堆** `logStandFoot 6A4A23` → 「扎在地里」 |
| **受光** | 受光边**横着一条**（落在上沿/左沿）                                | 受光边**竖着一条**（`logStandEdge D6A863`） —— 光从斜上方来                            |
| **端面** | 两端**切口**：深色外圈 `logEnd 5C4020` + 年轮芯 `logTop C09455` | 顶端**切面**：亮外圈 `logStandEdge` + 最亮芯 `logStandCap EDCB8C`（朝天的新鲜切面）         |

外加一条**成对原则**：受光亮边与背光暗边**永远成对**出现在主体的两侧。  
第一版把暗边一律画在下沿，结果竖躺（南北向）时它和下端切口叠成一团黑；  
改成成对之后，横躺时暗边天然落在下沿（顺带兼作「贴地」线索），竖躺时落在右沿（配成圆柱感）。

### 3.1 ⚠️ 一条必须守住的边界：视觉高度 = 玩法高度

`TRUNK_H = 1.00` 格 —— 立起来的树干**在画面上**就是一格高，  
因为它在**玩法上**就是一格高（`world` 里可以直接踩上去 / 跨不过去）。  
躺着的木头 `LOG_THICK = 0.50` 格同理，对应 `H_LOG_LAND = 0.5`。

**这两个数不能为了「好看」随便调** —— 调了就会出现  
「看着能踩上去、实际踩不上」这类**画面与规则的漂移**。要改就得连着玩法一起改。

### 3.2 过渡怎么做：代理池，不碰真实木头

倒 / 立的过程**不能直接改真实木头的控件** —— 真实木头是 `rebuildObjects()` 按格子数据重建的，  
每帧插值会被下一次重建覆盖掉。所以另起了一个**过渡代理池**：

- `state.objProxyCtrls` / `objProxyUsed`：代理控件池（在 `RESTACK_POOLS` 里，  
  必须挂在**世界容器**中才参与「近处压远处」的深度排序）；
- `M.setObjectAnim(act)`：按 `act.animFrom` / `act.animTo` 算出**起止两个形态**；
- `M.paintObjProxy()`：逐帧画插值形态；
- `M.animateObject(dt)`：播完清标志 + `rebuildObjects()`；否则 `paintObjProxy + restackWorld()`。

配套两个细节：

1. **`hideAnimAt(c, r)`**：过渡期间，终点格上的真实木头**先不画**（否则会和代理叠成两个自己）。  
   实现是「在 `rebuildObjects()` 里比对 `state.objAnimTo.c/r` 后跳过」。
2. **配色过渡用「盖一层」而不是「两边各降一半 alpha」**：  
   如果两头各 50% 透明度，中间态会露出底下的草地，读作「木头变透明了」；  
   改成躺色打底 255、再用 `aNew = floor(255 * stand)` 把立色盖上去，  
   全程不透明，只是在两套配色之间**硬切过渡**。

### 3.3 缓动与扬尘

- `easeBack(k, o)`：带回弹过冲的缓动。  
  `knock`（倒下）用 `DEFAULT_OBJ_ANIM_OVERSHOOT = 1.35`（「甩过头再落定」），  
  `raise` / `slide` 用 1.15（轻轻到位）。  
  时长 `DEFAULT_OBJ_ANIM_TIME = 0.22 s` —— **比小人走一格更长**，看得清。
- 过渡期间 `row`（深度键里的行）用 **raw 线性插值**而不是过冲插值 ——  
  否则过冲那一下会把木头`甩`到隔壁行去，前后遮挡会跳。
- 扬尘 `M.spawnDust(c, r, scale)`：撞倒 `1.5`（重）/ 立起·侧推 `0.85`（轻），  
  时长 `0.34 s`、初始直径 `0.62` 格、峰值 alpha `150`；  
  推进时 `grow = 1 + 0.85 * smoothstep(k)`、alpha 按 `(1-k)²` 衰减。  
  颜色 `dust E9DCBE` 刻意选**偏沙色** —— 压在绿草和青蓝海面上都读得出来。

## 5. 为什么 / 关键设计决定

1. **为什么不直接把树干画「小一点」** ——
   倒 / 立的对比要靠**多个维度同时作用**才稳。只改尺寸，在 34 px 的格子上会被抗锯齿糊掉；
   加上「亮边 vs 暗边」「竖切面 vs 横切口」「土堆」三组线索之后，**缩略图尺寸下也能读出来**。
2. **为什么代理池挂在世界容器** ——
   2.5D 的立体感全靠绘制顺序（`band + row*10 + sub`）。代理如果不进排序，
   落地那一瞬间会被前后行的地块盖住。
3. **为什么 `stand` 用「存在且为真」判立姿** ——
   `shapeOf(spec)` 里写的是 `if spec.stand then ... end`，
   所以「起点是立着的树」必须写 `stand = true`，`false` 和 `nil` 都会走躺姿。
   这条约定统一之后，`animFrom` / `animTo` 两个字段就两种写法，不容易写错。
4. **为什么不改 `world.lua` 的规则** ——
   用户要的是「对比更明显」，不是「玩法变了」。规则一动，三关最短解就得重算、
   e2e 口令就得重写、玩家手感也会变。**表现改动要能和玩法改动完全解耦**，
   所以过渡信息做成 `M.step()` 的**附加返回值**，旧调用方不读它也不受影响。

## 6. ⭐ 顺带修掉的一个真 bug（在 `_tools/test_editor_roundtrip.mjs` 里）

`_tools/test_editor_roundtrip.mjs` 原本有一行：

```js
globalThis.URL = { createObjectURL: () => '', revokeObjectURL: noop };
```

它把 Node 的 `URL` **构造器**整个换成了普通对象。Node 的文件系统垫片内部要做
`filePath instanceof URL`，一旦 `URL` 不是函数，`fs.readFileSync` 就抛
`TypeError: Right-hand side of 'instanceof' is not callable` —— **每次运行都必现**（在「全部 OK」之后崩）。

排查过程：先写最小复现脚本读一个非 ASCII 路径 → **正常**，说明不是路径编码问题；
再读测试源码定位到那一行；确认 `编辑器.html` 里 `URL` 只出现在「下载」按钮的 `click` 处理里
（本测试不会触发），于是**只补两个方法、保留构造器**：

```js
if (typeof globalThis.URL === "function" && !globalThis.URL.createObjectURL) {
    globalThis.URL.createObjectURL = () => "";
    globalThis.URL.revokeObjectURL = noop;
}
```

修完 `exit=0`，末尾正常打印「===== 往返自检：全部通过 =====」。

> 📌 这是**测试脚本自己的 bug**，与被测的 `编辑器.html` 无关，
> 但它会让「往返自检」这条防线**永远假失败**，所以必须一起修。

## 5. 为什么 / 关键设计决定

- **为什么用 `bare` 标记，而不是「另开一个数组」** —— 立着的东西**行为完全一样**
  （都是 1 格高、都会被撞倒、都朝前倒下一格），差别只在**来历与外观**。

- **为什么立起来的树干走纯色池而不是「干脆不给树叶素材」** —— 真机的树木是**美术素材元件**

  用三段矩形拼出一根木头 —— 与「撞倒后的树干」视觉同源（同三色 `logSide / logTop / logEnd`）。
- **为什么「推完前进一格」是必须的** —— 规则 ③ 原本只动木头不动小人，是**漏项**：
  木头顶多推一格，小人却原地不动，会把玩家卡在「推了但没上岛」的别扭状态。
  补上后「推」和「撞倒 → 顺势前挪」的体感一致。

> ★ **`DEFAULT_MAX_STEP = 0.25` 是这套改版的关键**：只有它 ≤ 0.25，
> 「树根 0.25 可踩 / 树干压地 0.5 不可踩」这条分界线才成立 ——
> 而这条分界线正是「撞倒 → 树干落水 → 踩过去」这条解法的支点。
>
> ★ **同一个「倒下的树」有两个高度**，按脚下是水还是陆地取：
> 漂在水上是 0.25（可踩 = 桥），压在陆地上是 0.5（跨不上 = 只能推）。
> 判定只有一处：`world.logHeightAt()`。

### 5.3 「木桩 / 立桩」概念被删掉了

老版本里 `stumps`（木桩）和 `stumpStanding`（立起的木桩）是**独立于树木**的物体。
新规则下 **立着与躺下只是同一棵树的两个状态**：

- 立着 → 存在 `state.trees`（1 格高）；
- 躺下 → 存在 `state.logs`（占一格，带 `dir` 说明躺向）。

所以 `world.lua` 里删掉了 `logIndexOf` / `logOnLand` / `logHeight` / `M.stumps`，
`step()` 里原来那套「先判能否踩上木桩，再判是否从端面推木桩」被合并进新的判定链：

```
撞树 → 能踩就踩 → 踩不上且目标格是倒下的树（正面立起 / 侧面滑一格）→ 石头 → 水 / 太高
```

三条必须如此的顺序理由（都写在 `world.step()` 的注释里）：

1. **「能踩就踩」排在「推」前面**：树干漂在水里时顶面 0.25，要直接走上去（这就是过水道）；
   压在陆地上时是 0.5，跨不上，才会落到「推」。同一个物体两种行为，差别全在脚下的水陆。
2. **「撞树」排第一**：立着的树永远 1.0 格高、永远跨不上去，所以只能撞、或者是由推倒的树干立起来。
3. **树根不算占位**（`world.isFree` 不看树根）：撞完原地留 0.25 的树根，木头可以直接盖在它上面，
   于是「推着树干滑过一处树根」是合法的。

### 5.4 关卡全部重设（`config.lua` 的 `M.LEVELS`）

三关共用同一张 22×13 地图，**岛间只隔 1 格水**（第 14 列），靠树 / 树干的位置与躺向分难度：

| 关 | 名字 | 教什么 | 最短解 | 步数 |
| --- | --- | --- | --- | --- |
| 01 | 起点草地 | **撞倒**：`(13,4)` 的树紧挨水道，朝右撞 → 树干落进 `(14,4)` | `DDDDDDDSSSDDDD` | 14 |
| 02 | 侧着推 | **侧面推**：`(11,5)` 预置南北向树干堵路，朝右推三次 → 滑进 `(14,5)` | `SDDDDDDDDDDSSDDDD` | 17 |
| 03 | 立起来的树 | **正面推**：`(12,5)` 预置东西向树干，朝右推 → 在 `(13,5)` 立起来 → 再撞倒进水道 | `SDDDDDDDDSSDDDD` | 15 |

三条口令都是 `_tools/solve_浮岛借木.py` 的 **IDA\* 搜出来的最短解**，不是手编排的；
脚本内置这三条做 `BUILTIN` 自检，并会告警「内置口令步数 ≠ 最短解步数」。

> 为什么用 IDA\* 而不是 BFS：**每推一次树干就多一个树根**，状态空间持续发散，BFS 撑不住。
> 改成「到终点的曼哈顿距离」当启发式 + 按剩余预算剪枝即可秒出。

### 4. 改了什么、为什么、怎么验证

#### 4.1 `_shared/_check_refs.py`（新增两节校验）

**为什么**：浮岛借木把「元件索引」拆成了三处同源——
`config.DEFAULT_PREFAB_*` ↔ `_tools/_sim_common.mjs` 的 `SIM_TEMPLATE_GUIDS`
↔ `_tools/qxqy_simsave.mjs` 的 `GUID_*`，
再加一份 `编辑器.html` 的 `DEFAULTS` 要跟 `config` 逐项一致。
这四份东西分散在四个文件，**手改必漂移**，所以做成自动校验。

**验证**：见 §6（这条是整批最有力的实证）。

#### 4.2 `_tools/_sim_common.mjs` / `qxqy_simsave.mjs`（模板 GUID 2 → 8 项）

**为什么**：模拟器原来只有 `rectPrefabId=2000001`、`textPrefabId=2000002` 两个自造 GUID。
真机内置模板的实际索引是 `1073741876`（容器节点）… `1073741886`（人物），
存档里要按**真机索引**建模板，模拟器才能等价复现真机行为。现在 8 项齐全：

| 真机索引 | 元件 | 模拟器键 |
| --- | --- | --- |
| `1073741876` | 容器节点 | `containerPrefabId` |
| `1073741894` | 图片·矩形（纯色底图首选） | `rectPrefabId` |
| `1073741870` | 图片（纯色底图回退） | `imagePrefabId` |
| `1073741868` | 文本框 | `textPrefabId` |
| `1073741879` | 图片·海水 | `waterPrefabId` |
| `1073741881` | 图片·草地 | `landPrefabId` |
| `1073741883` | 图片·树木 | `treePrefabId` |
| `1073741886` | 图片·人物 | `playerPrefabId` |

#### 4.3 `_tools/qxqy_mount.mjs`

**为什么**（三条独立的修复）：
1. **params 链路是断的** —— 脚本参数传不到工程里，靠 `buildParamShim` 兜底；
2. **按键注入**原来只能指定固定帧，现在支持逐键 `--key Foo@40`；帧号以引擎真实帧为准
   （默认先冻结实时钟），否则截图时机对不上；
3. **新增 `--probe-walk <帧>`**：打印控件名。这条是给「两个纯色底图模板模拟器渲染成同一张白矩形」
   准备的分辨手段 —— 只能靠控件名（`SIM_矩形` / `SIM_图片_回退`）区分，不能靠截图。

#### 4.4 新增的 4 个工具脚本

- `e2e_浮岛借木.sh`：把三关解法 + A/B + 提示 + 探针 7 轮串成一条命令，
  判据是**挂载无错**与**底图模板控件总数一致**。
- `preview_art_浮岛借木.py`：**这是本轮最重要的新增工具**。
  模拟器只代理 `100001–100006` 六个图源，画不出真美术，
  所以「素材有没有严丝合缝压在格子上」必须**离线**看。它从 `config.lua` 解析调色板 /
  `ART_FIT` / 关卡数据，用与 `level.lua` **同一套几何**渲染，输出 PNG。
  ⚠️ 改 `level.lua` 的几何后必须同步它，否则它会说假话。
- `make_grass_tile.py`：⚠️ 背景是**踩过的坑** —— AI 生成图把 `grass tile` 理解成等距菱形，
  铺到正交网格上是一片菱形格纹，调参救不回来。改为**程序化生成方形顶面**，
  并内置平铺自检（格内亮度极差 < 8，防止瓦片自带渐变变成条纹）。
- `make_compare_浮岛借木.py`：生成 A/B 对照图。
