# 第 13 批 · 头发终于有颜色了：量化把「银灰发」并进了「白皙皮肤」

## 1. 起因

需求原话：**「把头发等改成这种颜色而不是肤色」**。

第 12 批把调色板从 20 色去重到 13 色，画面确实清楚了，但代价是：
**「银灰头发」和「白皙皮肤」被并成了同一个 `#DCE2EE`**。
真机上整颗头一片浅白，看不出有头发 —— 看起来像「没头发 / 头发就是肤色」。

## 2. 先确认它确实被并掉了（量出来的，不是猜的）

用源图逐格量平均色（`_tools/restyle_hero.py` 的 `cell_colors()`，与生成器同一套并集裁剪）：

| 部位 | 源图平均色 | 冷暖（R−B） | 量化后落到 |
|---|---|---|---|
| 头发（头顶 / 刘海） | `(218,220,229)` | **−11（冷）** | `#DCE2EE` |
| 脸（眼周 / 下巴） | `(230,216,210)` | **+20（暖）** | `#DCE2EE` |

冷暖、亮度本来就分得开，但**去重把它们并到了同一个索引 11**。实测后果：
头部（前 15 行）该改色的浅色格 **409 格（四向合计）全是 `#DCE2EE`**，
和脸、和白裙没有任何区别；调色板里钉死的肤色 `#F2D8C4` 只在腰、手各落 2 格 —— 等于白留了一格。

> 所以这不是「画错了」，是**颜色预算被合并吃掉了**。要修的只是「重新给头发分颜色」，不是改形状。

## 3. 改法：只换颜色、不动几何

新增 `_tools/restyle_hero.py`（本批唯一新增脚本）。它读 `heroArt.lua`，
**一个坐标都不碰**，只改颜色号：

1. 头部 = 网格前 15 行（`HEAD_ROWS`）；再往下是脖子和裙子，不碰。
2. 格当前是「浅色」（索引 6/8/9/11/12）且**源图该格不暖**（R−B < 12）→ 判定为头发。
3. 发色分两档，按源图该格亮度 ≥ 200 分档：亮 `#C2C9DC` / 暗 `#9AA3BE` —— 保住头发的明暗层次。
4. **脸保护**：行 9~14、列 18%~80%、源图 R−B ≥ 6 的格**保持原色不动**；
   背面朝上（`W`）没有脸，整颗头都算头发（`FACES_WITH_FACE`）。
5. 按格判色后重做一次行 RLE 合并 → 同一块里不同色的格会拆成两块。

结果是 **块数略增、实心格一个不变**：

| 朝向 | 块数 | 实心格 |
|---|---|---|
| S 正面 | 146 → **165**（+19） | 不变 |
| W 背面 | 134 → **147**（+13） | 不变 |
| A 左视 | 119 → **145**（+26） | 不变 |
| D 右视 | 113 → **137**（+24） | 不变 |

> 这就是它和「整份重新生成一遍」的区别：轮廓、五官位置、清晰度**零回归**，
> 只是把同一批格子换了个颜色。想换发色也只改调色板 13/14 两行 hex，或用参数重跑。

配套：`level.lua` 的 `M.BUILD` 从 `b12` 升到 **`b13`** —— 真机日志一眼能看出导入的是不是这一版。

# 第 12 批 · 小人更清晰、更贴原图：调色板去重 + 网格回到 28 行

## 1. 起因

需求原话：**「让小人变得更清晰，且更接近我给你的图片中展示的样子」**。

第 8 批把四张立绘压成像素画时选了 `ROWS = 32` / 12 色，画面里小人是一团偏白的块，
五官和头冠都读不出来。

## 2. 排查：先量屏幕，再决定改什么

实测 1280×720 下小人非草像素 bbox = **约 52 × 54 px**（1 格高）。这条数字改变了一切：

- 32 行 → 每块 ≈ 1.7 屏像素；40 行 → 1.35；48 行 → 1.13。
- **每块不足 2 个屏幕像素时，引擎的抗锯齿会把相邻块糊成一片**，
  于是「加密」不但没用，画面上反而**更糊**（32 / 40 / 48 三版在游戏里几乎分不出来，
  28 行那版反而最「利」）。

结论：清晰度的瓶颈不在网格精度，而在**颜色预算**。

## 3. 真正的根因：12 个调色板里有 5 个是「同一个白」

`k-means` 只看 RGB 距离，角色整身浅色 → 它把 `#F5F8FB`、`#F3F6FA`、`#EEF2F7`、
`#E0E6F1` 这些**肉眼完全同一个白**各占一格。结果是：

- 10 个名额用来描述「白 + 灰」，**蓝色头冠、蓝眼睛、裙摆青蓝只剩 2 个名额**；
- 白色之间那点差异在 1 格像素上根本看不出来，纯属浪费。

## 4. 改法（两个文件 + 一个工具参数）

| 改动 | 位置 | 说明 |
|---|---|---|
| **调色板去重** `--pal-dedupe 24` | `_tools/make_hero_pixels.py` | k-means 之后把「距离 < 24 的两个色」并成一个（加权平均），再按亮度重排。**20 → 13 色**，省下的名额自动还给了有色相的颜色 |
| 网格 `ROWS = 28` / `COLS = 17` | 同上（`--rows 28`） | 每块 ≈ 2 屏像素，边缘不再被糊平 |
| 内置数据重生成 | `_tools/emit_hero_builtin.py` | 字符表 `0123456789ab` → `0123456789a…v`（最多 32 色），`--write` 重写 `level.lua` 的 `HERO_BUILTIN` 段 |
| 版本戳 `b11` → `b12` | `level.lua` | 真机日志能分辨用没用上新文件 |

顺带把生成器做成**全参数化**（`--k / --pal-dedupe / --dark-share / --denoise / --cover /
--merge-tol / --out / --preview`），以后调小人不用改代码。

**块数反而少了**：187 → **146**（正面），控件压力更小。

## 5. 验证

| 项 | 结果 |
|---|---|
| 静态三连 | blocks=0 / refs=0 / scope=0 |
| 模拟器挂载 | `mountError: null`、`版本 level=b12 \| heroArt 脚本=有` |
| 自检日志 | `小人=像素画 \| 像素块=146 \| 数据源=heroArt 模块 \| 原因=无` |
| 画面 | 32 / 40 / 28 三版同机位截图对比，28 行版轮廓最利、头冠与裙摆层次可辨 |
| 玩法 | **零改动**：`world.lua` / `config.lua` / `编辑器.html` 都没碰，三关最短解仍 14/14/14 |

## 6. 教训（已写进 README §2.5）

- **先量屏幕像素，再谈分辨率**。角色只有 54 px 高时，`ROWS > 30` 的收益是负的。
- **k-means 的 k 不等于「有效颜色数」**。浅色主题下必须去重，否则颜色预算被近白吃光。
- 想让人物真正「变大变清楚」，只能改玩法尺度（格子大小），不是改 `ROWS`。

# 第 11 批 · 像素画不再依赖「新脚本」：数据内联进 `level.lua`，只覆盖原有文件就能显示

## 1. 起因

第 10 批修了「真机没填参数返回 0」之后，用户重新导入 `game.lua`，画面**仍是橙色方块**。

橙色不是随便什么颜色：`config.DEFAULT_PALETTE.playerBody = "F2A03C"`，全工程**只有一处**
使用它（`level.lua` 的纯色回退分支）。所以「橙色块」= **像素画失败 + 立绘失败**同时发生。

顺这条线检查第 8 批的设计，找到真正的结构性弱点：

> 像素画数据只存在于 `heroArt.lua`，而它是第 8 批**唯一新增**的脚本。
> 真机上只要这个脚本没建 / 文件名不对 / 编译失败，`require` 就拿不到，
> 小人立刻退回立绘；如果这台客户端连「人物」素材元件（`1073741886`）也拿不到，

# 第 10 批 · 「还是橙色块」的真正原因：真机面板没填的参数返回 **0**，把默认开的东西全关了

## 1. 起因

> 画面是仍是橙色块，请查清原因，并做修改

## 2. 先定位「橙色块」是哪条分支

`buildPlayer` 只有三条路：

| 分支 | 条件 | 小人长什么样 |
|---|---|---|
| **像素画** | `state.heroPixel` 为真 | 187 块纯色矩形拼的人 |
| **立绘** | `state.playerCtrlArt` 为真 | 「人物」素材元件自带立绘 |
| **纯色回退** | 以上都不成立 | **`F2A03C` 橙色身体矩形 + `3A2A20` 深色头** |

`config.DEFAULT_PALETTE.playerBody = "F2A03C"` —— **正是用户描述的橙色**。
所以橙色块 ⇒ 走的是第三条 ⇒ `heroPixel` 与 `playerCtrlArt` **同时为假**。

## 3. 根因：`getParamNumber` 的默认值挡不住「数字 0」

原代码：

```lua
function getParamNumber(name, default)
    local v = script:GetParam(name)
    if type(v) == "number" then return v end   -- ← 0 也是 number，原样返回
    ...
    return default                              -- ← 只有"非数字"才用默认
end
```

**真机脚本参数面板里，没填的数字参数返回 `0`（不是 `nil`）。**
`type(0) == "number"` → 直接返回 0，于是：

```lua
state.useArt     = (getParamNumber("useArt", 1) or 0) > 0        -- 0 > 0 = false
state.heroPixelOn = (getParamNumber("heroPixelOn", 1) or 0) > 0  -- false
state.view25d     = (getParamNumber("view25d", 1) or 0) > 0      -- false
```

四个「默认开」的开关在**没配参数的真机上集体变 false**。后果和用户看到的现象逐条对上：

| 开关被误关 | 表现 |
|---|---|
| `useArt = false` | 海水 / 草地 / 树木 / **人物**全部退回纯色矩形 → 小人变橙块 |
| `heroPixelOn = false` | 像素画根本不画 |
| `view25d = false` | 岛没有厚度侧面（平面视角） |

这也解释了为什么第 7 批（`SetImage` 换立绘）同样"看起来没生效"：那条路也要求
`playerCtrlArt = true`，而它同样被 `useArt = false` 挡住了 —— **问题不在小人，在参数**。

> ★ 这条根因同样解释了「元件索引」那一类：`containerPrefabId / playerPrefabId` 等
> 读到 0 时，容器与素材控件全走回退，所以画面"能跑但全是纯色"。

## 4. 改法：`0` 视为「没配」，关闭改成 `-1`

`game.lua` 新增两个 helper，所有读取点统一走它们：

```lua
local function paramSwitch(name, dflt)   -- 开关：nil / 0 → 用 dflt；>0 开；<0 关
local function paramId(name, dflt)       -- 索引：nil / <=0 → 用 dflt
```

- 覆盖：`containerPrefabId` `rectPrefabId` `imagePrefabId` `textPrefabId`
  `water/land/tree/playerPrefabId` + `useArt` `heroPixelOn` `view25d` `waterGridLines`
- **`rectImageId` 不动**：它的 `0` 是有效值（= 不改图源）
- 音效 ID 不动：`0` = 无音效

### ⚠️ 约定变更（使用方必须知道）

| 参数 | 旧 | 新 |
|---|---|---|
| `useArt` | `0` = 关 | **`0` / 空 = 没配（= 开）**；**`-1` = 关** |
| `heroPixelOn` | `0` = 退回立绘 | **`-1` = 退回立绘** |
| `view25d` | `0` = 平面 | **`-1` = 平面** |
| `waterGridLines` | `0` = 旧棋盘 | **`-1` = 旧棋盘** |

## 5. 新增「参数快照」日志（和上一批的自检配成一对）

```
[浮岛借木] 参数 useArt=true heroPixelOn=true view25d=true | 元件 rect=1073741894 container=1073741876 player=1073741886
[浮岛借木] 小人=像素画 | 像素块=187 | 原因=无
```

第一行说「参数读到了什么、元件索引是多少」，第二行说「最后走了哪条路」。
以后再遇到「画面不对」，这两行就能直接定位，不用再猜。

## 6. 验证（模拟器 3 个用例）

| 用例 | 期望 | 实测 |
|---|---|---|
| **八个参数全传 `0`**（精确模拟真机面板没填） | 全按默认 → 像素画 | ✅ `useArt=true heroPixelOn=true view25d=true`，`像素块=187`，截图与第 8 批逐像素一致 |
| `heroPixelOn=-1, useArt=-1, view25d=-1` | 走纯色回退（= 用户之前的橙块） | ✅ `useArt=false heroPixelOn=false view25d=false`，`像素块=0`，截图就是 **F2A03C 橙块** |
| 默认（不传参数） | 像素画 | ✅ |

> 右 = 修复后的像素画）。这张图也是这次根因判断的直接证据。

# 第 9 批 · 「像素小人没显示」：真机兜底 + 一行自检（不改玩法、不改画面）

## 1. 起因

> 为什么我把 lua 脚本导入后，像素小人没有显示出来

## 2. 结论：不是「画错了」，是**四道门静默回退**了

像素画是**可选表现层**。第 8 批为了「一个表现层不许把整关拖崩」，把失败全做成了
静默回退 —— 好处是不会因为一个表现层把整关拖崩，**代价是它不报错，只安静地变回老样子**，
从画面上根本看不出断在哪。

`buildPlayer` 里按顺序有四道门，任何一道没过都会回退：

| # | 门 | 断了画面会怎样 | 真机上最常见的触发 |
|---|---|---|---|
| 1 | `require("heroArt")` 成功且是 table | 退回立绘（**有**小人） | **`heroArt.lua` 没导入** —— 第 8 批唯一**新增**的脚本，编辑器里要单独新建同名脚本 |
| 2 | `heroPixelOn > 0` | 退回立绘（**有**小人） | 脚本参数面板里的旧值 `0` 覆盖了 `config` 的默认值 `1` |
| 3 | `ensureHeroBox()` 拿到画布容器 | 退回立绘（**有**小人） | `containerPrefabId = 0`（见 §3 缺陷 A） |
| 4 | `repaintPlayerArt()` 真画出来了 | **小人凭空消失** | 真机控件数超限，一块都没建出来（见 §3 缺陷 B） |

所以「没显示」有两种完全不同的样子，**先看画面里还有没有人**：
还有小人（只是变成老立绘 / 橙色块）→ 第 1～3 道门；连人都没了 → 第 4 道门。

## 3. 顺着这次反馈修掉的两个**真实缺陷**（代码里的不对称，不是猜的）

### 缺陷 A：画布容器**没有回退**，全世界只有它搞特殊

`game.lua` 的 `createContainer()` 一直是**两级回退**（容器节点 → 矩形全透明），
但第 8 批新写的 `ensureHeroBox()` 写的是 `if cid <= 0 then return false end` ——
**容器节点拿不到就直接放弃像素画**。

而 `containerPrefabId` 恰恰是「脚本参数面板留空 / 老存档没登记」时最容易变成 `0` 的那一项。
偏偏这时**世界容器自己已经回退成功了**，画面一切正常，只有小人悄悄变回立绘 ——
这是最难查的一类：什么都不报，只有一处表现层不对。

→ 现在 `ensureHeroBox()` 与 `createContainer()` **同源**：拿不到容器节点就退回
「矩形 + 全透明」当坐标系宿主（容器只是个坐标系，看不见也不影响）。

### 缺陷 B：像素块**一块都没建出来**时，小人会蒸发

第 8 批的顺序是「先隐藏立绘 → 再画像素」，但 `buildPlayer` **不看
`repaintPlayerArt()` 的返回值**。真机控件数逼近上限时 `poolGet` 全部返回 nil，
187 块一块也没画成 → **立绘已隐藏 + 像素块 = 0 = 小人没了**，比回退立绘糟得多。

→ `repaintPlayerArt()` 现在会**主动认输**：

- 连续 8 块创建失败就停（不在真机上白试一百多次）；
- 画出来的块数 **< 总块数的一半** → 清池、隐藏画布、`return false`。

→ `buildPlayer` 收到 `false` 就把 `heroPixel` 降回 false，**走立绘分支**。
一句话：宁可显示老立绘，也绝不留一个空白。

## 4. 新增：启动时打一行自检

```
[浮岛借木] 小人=像素画 | 像素块=187 | 原因=无
```

- 只打一次（`state.heroPixelLogged`），不刷日志；
- 回退时 `原因=` 直接写人话，一一对应 §2 的四道门；
- `print` 在个别沙箱里可能被裁掉 → 先 `type(print) == "function"` 再调，`pcall` 兜住；
- 原因同时留在 `state.heroPixelWhy`，**没有日志面板也能靠「小人是什么形态」反推**。

## 5. 排查顺序（已写进 `浮岛借木/README.md` §2.5.1）

1. 编辑器里**有没有 `heroArt` 这个脚本**（新增文件，最容易漏）
2. `heroPixelOn` 是不是被脚本参数面板改成了 `0`
3. 导入的是不是**收件箱**这份（仓库根 `浮岛借木/` 是 09-30 基线，**没有像素画代码**）
4. 看脚本日志那行自检，`原因=` 会直接说断在哪

# 第 8 批 · 小人不再引用图片：改用纯色矩形「画」出四向像素画

## 1. 需求原文

> 在代码中用绘画的方式把上面的四张图片放进游戏中并实现上面要求的效果，而不是直接引用图片

（「上面要求」= 第 7 批那条：向下走用正面、向右走用右视、向左走用左视、向上走用背面，
以此实现转身；并去掉走动时脚下的白色方框。）

## 2. 与第 7 批的关系：**同一批立绘，换了一种落地方式**

| | 第 7 批 | 第 8 批（本批） |
|---|---|---|
| 角色怎么显示 | `SetImage` 引用 4 张 PNG 图源 | **几十块纯色矩形拼出来**（`heroArt.lua` 的数据） |
| 真机要准备什么 | 上传图库 + 手工填 4 个图片 ID | **什么都不用**：没有图片 ID、没有图库 |
| 转身 | 换图源 | 换一套矩形重画 |
| 模拟器里能看见吗 | ✗ 只能看到元件的代理色块 | **✓ 能看见**（像素画就是矩形，模拟器代理 100001 图元） |

⚠️ **合并顺序**：若第 7 批已合并，第 8 批会**删掉** `playerImageS/W/A/D` 四个参数与
`applyPlayerImage()`；若两批一起合，请**直接采纳第 8 批**（第 7 批的 `SetImage` 路径已作废）。
四张 PNG 素材**保留**，但用途从「运行时图源」变成「`make_hero_pixels.py` 的输入」。

## 3. 数据从哪来：`_tools/make_hero_pixels.py` → `heroArt.lua`

四张立绘 → 12 色调色板 + 网格上的矩形表。**五个关键工艺**（每一步都为一个具体问题）：

1. **四张一起聚类**出调色板 —— 分开聚类的话，转身时头发会从银白跳到灰白。
2. **肤色锚色钉死** `#F2D8C4` —— 角色整身都是浅色，k-means 会把「暖白皮肤」并进
   「冷白裙」，脸就和头发糊成一团（试过，糊得认不出）。
3. **每格取众数、不取平均** —— 平均会把深色描边和瞳孔一起抹淡。
4. **暗色优先**：格内暗像素占比 ≥16% 就改用「暗像素的众数」—— 决定「能不能看出五官」。
5. **3×3 众数滤波 + 贪心矩形合并**（行 RLE → 向下合并同色同宽）——
   控件数从「像素数」压到「色块数」：一格裙摆是一块矩形，不是二十个小方块。

产物：`COLS=20 × ROWS=32` 的网格、12 色、四向各 **160~190 块**矩形。

## 4. 运行时怎么画（`level.lua`）

```
素材/*.png ──make_hero_pixels.py──▶ heroArt.lua ──repaintPlayerArt()──▶ 矩形池
                                                                    │
                                              heroArtBox（容器，每帧只移动它）
```

- 一块的边长 = `cellSize / ROWS` → 角色**恒 1 格高**，格子怎么自适应都不变形（像素恒正方）。
- 网格坐标（左上原点、y 向下）→ 容器坐标（中心原点、y 向上），画布**底边压在脚线上**。
- 换朝向 = `setPlayerFacing()` → `repaintPlayerArt()`：**重画一套矩形**，不新建控件（走对象池）。
- 每块往外扩 `0.1 格像素`：亚像素矩形挨着摆，真机会在缝里露出底色（一条条亮线）。

**为什么装一个容器**：小人每帧都在动。若每块各自 `SetAnchoredPosition`，一帧几十次调用；
装进 `heroArtBox` 后每帧只移动 1 个控件，像素块坐标一次算死。
容器挂在 `containerWorld` 里并参与 `restackWorld()`（`SUB_PLAYER`），
所以「前面的树挡住后面的小人」仍然成立。

## 5. 回退链（任何一环断掉都不会整片空白）

`heroArt.lua` 缺失 / 脚本参数 `heroPixelOn=0` → 用 `playerPrefabId`（人物元件）自带的立绘
→ 连「人物」元件都没有 → 纯色身体矩形 + 头（加素材之前的老画面）。

## 6. 三处同源（改一处必须同步另外两处）

| 位置 | 作用 |
|---|---|
| `level.lua` 的 `repaintPlayerArt()` | 真机绘制 |

## ③ 为什么是「换图」而不是「转角度」

千星没有「把立绘转到 45°」这种能力，`rotationZ` 转出来是歪的（正交 2D 立绘转了就穿帮）。  
四张同角度立绘 + 换图是唯一能做出「转身」的路子。

代价是**四张必须同画布、同留白**（本工程都是 1024×1536 原图 → 存 512×768），  
尺寸统一交给一套系数，**不许逐张调**：

```
DEFAULT_ART_FIT.player = { w = 0.751, h = 1.126, dy = 0.508 }
   w / h = 0.6667 = 1024 / 1536（必须严格相等，否则立绘被拉变形）
   内容高 1364 / 1536 = 0.888  →  1 / 0.888 = 1.126（内容正好 1 格高）
   内容底边 1461 − 画布中心 768 = 693 / 1536 × 1.126 = 0.508（脚踩在脚线上）
```

（旧的 `人物.png` 是 1024×1024 的单图、系数 1.707；换成 2:3 画布后必须重算，  
**手调一定会出错**，所以 `_tmp/make_hero_art.py` 里是抠完图自动反算并打印的。）

## ④ 抠图：为什么不能「近白就透明」

四张是 **JPG 白底**，直接当图源 = 游戏里一个白方块。但角色本身大量纯白（银发、白裙蕾丝），  
用「所有近白都变透明」的阈值法会把头发和裙子打穿。

所以只从**画布边缘**做 flood fill（4 个种子点，thresh 26），**与边缘连通的近白**才算背景；  
角色内部的白不连通边缘 → 一定保得住。再用 3×3 最小值滤波把 alpha 边界向内收 1px，  
去掉 JPG 抗锯齿留下的那圈白边。

产物：512×768 透明 PNG，四张合计 ~1.5 MB（原图 4.6 MB，游戏里一格只有 34–44 px，  
留 10 倍余量纯属浪费）。

## ⑤ 白框（涟漪）为什么直接关掉

涟漪是**一块纯白矩形** —— 图元只有矩形，画不出圆。它铺在小人脚下，真机上看起来就是  
「脚下一个白框」，把草地和角色的脚一起糊住。

- `DEFAULT_FX_RIPPLE_ON = 0`（要临时看就改 1）

- **控件仍然常驻创建** → 控件总数不变 → `e2e` 的探针数（522 / 522）不变

## 3. 核心：同一根木头的「两个姿态」

第 5 批已经把「立着的也是一根**无叶树干**」这件事在**规则层**做对了（`tree.bare` 标记）。  
本批解决的是**表现层**：光「没有树叶」还不够，玩家一眼扫过去还是容易把两者看成一回事。

所以给同一根木头立了**两套完全不同的形状 + 配色语言**，四个维度同时拉开：

| 维度     | 躺着的木头                                               | 立起来的树干                                                                  |
| ------ | --------------------------------------------------- | ----------------------------------------------------------------------- |
| **剪影** | 长而扁 `1.00 × 0.50` 格（横着一段）                           | 窄而高 `0.36 × 1.00` 格（竖着一截）                                               |
| **明暗** | 暗一档的旧木色 `logSide 9C6C36` + **贴地暗边** → 「躺在地上的旧木头」    | 亮一档的新木色 `logStandSide AB7A3E` + **根部土堆** `logStandFoot 6A4A23` → 「扎在地里」 |
| **受光** | 受光边**横着一条**（落在上沿/左沿）                                | 受光边**竖着一条**（`logStandEdge D6A863`） —— 光从斜上方来                            |
| **端面** | 两端**切口**：深色外圈 `logEnd 5C4020` + 年轮芯 `logTop C09455` | 顶端**切面**：亮外圈 `logStandEdge` + 最亮芯 `logStandCap EDCB8C`（朝天的新鲜切面）         |

外加一条**成对原则**：受光亮边与背光暗边**永远成对**出现在主体的两侧。  
第一版把暗边一律画在下沿，结果竖躺（南北向）时它和下端切口叠成一团黑；  
改成成对之后，横躺时暗边天然落在下沿（顺带兼作「贴地」线索），竖躺时落在右沿（配成圆柱感）。

### 3.1 ⚠️ 一条必须守住的边界：视觉高度 = 玩法高度

`TRUNK_H = 1.00` 格 —— 立起来的树干**在画面上**就是一格高，  
因为它在**玩法上**就是一格高（`world` 里可以直接踩上去 / 跨不过去）。  
躺着的木头 `LOG_THICK = 0.50` 格同理，对应 `H_LOG_LAND = 0.5`。

**这两个数不能为了「好看」随便调** —— 调了就会出现  
「看着能踩上去、实际踩不上」这类**画面与规则的漂移**。要改就得连着玩法一起改。

### 3.2 过渡怎么做：代理池，不碰真实木头

倒 / 立的过程**不能直接改真实木头的控件** —— 真实木头是 `rebuildObjects()` 按格子数据重建的，  
每帧插值会被下一次重建覆盖掉。所以另起了一个**过渡代理池**：

- `state.objProxyCtrls` / `objProxyUsed`：代理控件池（在 `RESTACK_POOLS` 里，  
  必须挂在**世界容器**中才参与「近处压远处」的深度排序）；
- `M.setObjectAnim(act)`：按 `act.animFrom` / `act.animTo` 算出**起止两个形态**；
- `M.paintObjProxy()`：逐帧画插值形态；
- `M.animateObject(dt)`：播完清标志 + `rebuildObjects()`；否则 `paintObjProxy + restackWorld()`。

配套两个细节：

1. **`hideAnimAt(c, r)`**：过渡期间，终点格上的真实木头**先不画**（否则会和代理叠成两个自己）。  
   实现是「在 `rebuildObjects()` 里比对 `state.objAnimTo.c/r` 后跳过」。
2. **配色过渡用「盖一层」而不是「两边各降一半 alpha」**：  
   如果两头各 50% 透明度，中间态会露出底下的草地，读作「木头变透明了」；  
   改成躺色打底 255、再用 `aNew = floor(255 * stand)` 把立色盖上去，  
   全程不透明，只是在两套配色之间**硬切过渡**。

### 3.3 缓动与扬尘

- `easeBack(k, o)`：带回弹过冲的缓动。  
  `knock`（倒下）用 `DEFAULT_OBJ_ANIM_OVERSHOOT = 1.35`（「甩过头再落定」），  
  `raise` / `slide` 用 1.15（轻轻到位）。  
  时长 `DEFAULT_OBJ_ANIM_TIME = 0.22 s` —— **比小人走一格更长**，看得清。
- 过渡期间 `row`（深度键里的行）用 **raw 线性插值**而不是过冲插值 ——  
  否则过冲那一下会把木头`甩`到隔壁行去，前后遮挡会跳。
- 扬尘 `M.spawnDust(c, r, scale)`：撞倒 `1.5`（重）/ 立起·侧推 `0.85`（轻），  
  时长 `0.34 s`、初始直径 `0.62` 格、峰值 alpha `150`；  
  推进时 `grow = 1 + 0.85 * smoothstep(k)`、alpha 按 `(1-k)²` 衰减。  
  颜色 `dust E9DCBE` 刻意选**偏沙色** —— 压在绿草和青蓝海面上都读得出来。

## 5. 为什么 / 关键设计决定

1. **为什么不直接把树干画「小一点」** ——
   倒 / 立的对比要靠**多个维度同时作用**才稳。只改尺寸，在 34 px 的格子上会被抗锯齿糊掉；
   加上「亮边 vs 暗边」「竖切面 vs 横切口」「土堆」三组线索之后，**缩略图尺寸下也能读出来**。
2. **为什么代理池挂在世界容器** ——
   2.5D 的立体感全靠绘制顺序（`band + row*10 + sub`）。代理如果不进排序，
   落地那一瞬间会被前后行的地块盖住。
3. **为什么 `stand` 用「存在且为真」判立姿** ——
   `shapeOf(spec)` 里写的是 `if spec.stand then ... end`，
   所以「起点是立着的树」必须写 `stand = true`，`false` 和 `nil` 都会走躺姿。
   这条约定统一之后，`animFrom` / `animTo` 两个字段就两种写法，不容易写错。
4. **为什么不改 `world.lua` 的规则** ——
   用户要的是「对比更明显」，不是「玩法变了」。规则一动，三关最短解就得重算、
   e2e 口令就得重写、玩家手感也会变。**表现改动要能和玩法改动完全解耦**，
   所以过渡信息做成 `M.step()` 的**附加返回值**，旧调用方不读它也不受影响。

## 6. ⭐ 顺带修掉的一个真 bug（在 `_tools/test_editor_roundtrip.mjs` 里）

`_tools/test_editor_roundtrip.mjs` 原本有一行：

```js
globalThis.URL = { createObjectURL: () => '', revokeObjectURL: noop };
```

它把 Node 的 `URL` **构造器**整个换成了普通对象。Node 的文件系统垫片内部要做

（本测试不会触发），于是**只补两个方法、保留构造器**：

```js
if (typeof globalThis.URL === "function" && !globalThis.URL.createObjectURL) {
    globalThis.URL.createObjectURL = () => "";
    globalThis.URL.revokeObjectURL = noop;
}
```

修完 `exit=0`，末尾正常打印「===== 往返自检：全部通过 =====」。

> ★ **`DEFAULT_MAX_STEP = 0.25` 是这套改版的关键**：只有它 ≤ 0.25，

> 而这条分界线正是「撞倒 → 树干落水 → 踩过去」这条解法的支点。

### 5.3 「木桩 / 立桩」概念被删掉了

老版本里 `stumps`（木桩）和 `stumpStanding`（立起的木桩）是**独立于树木**的物体。
新规则下 **立着与躺下只是同一棵树的两个状态**：

- 立着 → 存在 `state.trees`（1 格高）；
- 躺下 → 存在 `state.logs`（占一格，带 `dir` 说明躺向）。

所以 `world.lua` 里删掉了 `logIndexOf` / `logOnLand` / `logHeight` / `M.stumps`，
`step()` 里原来那套「先判能否踩上木桩，再判是否从端面推木桩」被合并进新的判定链：

```
撞树 → 能踩就踩 → 踩不上且目标格是倒下的树（正面立起 / 侧面滑一格）→ 石头 → 水 / 太高
```

三条必须如此的顺序理由（都写在 `world.step()` 的注释里）：

1. **「能踩就踩」排在「推」前面**：树干漂在水里时顶面 0.25，要直接走上去（这就是过水道）；
   压在陆地上时是 0.5，跨不上，才会落到「推」。同一个物体两种行为，差别全在脚下的水陆。
2. **「撞树」排第一**：立着的树永远 1.0 格高、永远跨不上去，所以只能撞、或者是由推倒的树干立起来。
3. **树根不算占位**（`world.isFree` 不看树根）：撞完原地留 0.25 的树根，木头可以直接盖在它上面，
   于是「推着树干滑过一处树根」是合法的。

### 5.4 关卡全部重设（`config.lua` 的 `M.LEVELS`）

三关共用同一张 22×13 地图，**岛间只隔 1 格水**（第 14 列），靠树 / 树干的位置与躺向分难度：

| 关 | 名字 | 教什么 | 最短解 | 步数 |
| --- | --- | --- | --- | --- |
| 01 | 起点草地 | **撞倒**：`(13,4)` 的树紧挨水道，朝右撞 → 树干落进 `(14,4)` | `DDDDDDDSSSDDDD` | 14 |
| 02 | 侧着推 | **侧面推**：`(11,5)` 预置南北向树干堵路，朝右推三次 → 滑进 `(14,5)` | `SDDDDDDDDDDSSDDDD` | 17 |
| 03 | 立起来的树 | **正面推**：`(12,5)` 预置东西向树干，朝右推 → 在 `(13,5)` 立起来 → 再撞倒进水道 | `SDDDDDDDDSSDDDD` | 15 |

三条口令都是 `_tools/solve_浮岛借木.py` 的 **IDA\* 搜出来的最短解**，不是手编排的；
